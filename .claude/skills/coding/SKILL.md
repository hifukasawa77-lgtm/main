# コーディングスキル集

素のHTML / CSS / JavaScript（フレームワーク不使用）環境でのコーディングガイドライン。

---

## Skill: デバッグ手順 (Debug Workflow)
- **概要**: ブラウザ開発者ツールを最大限活用し、効率よくバグを特定・修正する。
- **実装要件**:
  - `console.log` の乱用を避け、`console.table` / `console.group` / `console.time` を用途別に使い分けること。
  - Canvas / アニメーション系のバグは `requestAnimationFrame` を一時停止（フラグ制御）して静止状態で検証すること。
  - イベントリスナーのデバッグは `getEventListeners(element)` (DevTools コンソール) で登録済みリスナーを確認すること。
  - エラーは必ず `try/catch` で捕捉し、ユーザーに見えないサイレントエラーを作らないこと。**`catch` のユーザー向けメッセージには例外の要旨（`err && err.message`）を必ず含める**。「操作を完了できませんでした」だけのフラッシュは原因追跡の手がかりをゼロにし、同じ症状の再報告を招く（戦国風雲記 ターン終了バグ PR #288→#289 で実証）。
  - **同じ症状を2回直したら、1回目は対症療法だったと判断する**: 欠損データ1件を埋めて直った・特定シナリオだけ直した、という修正で再発したら、個別データではなく**その欠損が生まれる経路**を疑うこと。「この1件」で止めず、同種の欠損が起きうる全経路（後から追加されるマスタ・ユーザー編集・外部取込）を洗い出して構造で塞ぐ（PR #288 は木曽家1家の洲を追加しただけで、翌コミットで別大名・別武将でも同じ例外が再発した）。
  - **「操作するたびに状態が悪化する」は非冪等な再試行のシグネチャ**: ボタンを押すたびに所持金だけ増える・件数だけ増える等は、多段処理の途中で例外が出て**前半の副作用だけ確定**していることを示す。原因箇所の特定より先に、その処理がトランザクション化されているか（後述）を確認すると当たりが早い。

## Skill: リファクタリングパターン (Refactoring Patterns)
- **概要**: 読みやすく保守しやすいコードへ改善するための指針。
- **実装要件**:
  - 同じロジックが3箇所以上出現したら関数化する（DRY原則）。ただし1〜2箇所の重複は無理に抽象化しない。
  - グローバル変数は最小限にとどめ、関連する状態は1つのオブジェクト（例: `const state = {}`）にまとめること。
  - 副作用のない純粋関数（同じ入力→同じ出力）を優先し、DOM操作や状態変更は呼び出し元に委ねること。
  - マジックナンバーは `const CANVAS_WIDTH = 800` のように名前付き定数に置き換えること。

## Skill: 外部データ取込のマッチング (Data Import Matching)
- **概要**: CSV等の外部データを既存エンティティへ取り込む際のマッチング設計（戦国の野望 CSV取込の件数不一致・データ損失バグで実証）。
- **実装要件**:
  - 「主キー一致 → 曖昧キー（グループキー）でフォールバック」型のマッチングでは、曖昧キー側に **claimed（割当済み）チェック**を必ず入れること。無いと同じ曖昧キーの複数行が同一エンティティへ潰れて順に上書きされ、既存データ損失と件数不一致を併発する。
  - 行→エンティティIDの割当は取込の最初に**一括計算**し、新規作成・値反映・件数集計の全フェーズで同じ割当を使うこと（フェーズごとに再マッチングしない）。これで「入力行数＝処理件数」の保証が立つ。
  - 検証は報告件数（反映N件・新規M件）と取込後の一覧実件数の突き合わせ、および既存エンティティ名が消えていないことの確認で行う。
  - **取込成功後は派生キャッシュを明示破棄する**: 取込がデータを正しく書き換えても、描画側のレイアウト/合成キャッシュが残っていると画面が変わらず「押しても反映しない」と報告される。キャッシュキーの変化やTTL（0.5秒等の安全リフレッシュ）任せにせず、取込完了時に依存キャッシュを明示的に無効化すること（データ更新経路とキャッシュ無効化を同じ関数内に置く）。
  - **取込はユーザーが削除したエンティティを復活させてはならない**: 起動のたびに走る取込（CSV等）は「元データにあるから作る」だけの実装だと、ユーザーが削除した項目を毎回マスタ側にだけ復活させる。永続データ側は削除済みのままなので、**取込が自ら不整合を作り出す**（戦国風雲記の削除済み城が復活してターン処理を落とした件で実証）。削除済みIDの集合を永続化し、取込の新規作成・既存更新の**両経路**でスキップすること。

## Skill: 永続状態とマスタデータの整合 (Persistent State vs. Evolving Master Data)
- **概要**: `localStorage` のセーブ等の永続データは**保存時点のスナップショット**である一方、コード側のマスタ（DATA）はリリースのたびに増え、ユーザー編集でも動く。両者がずれると `undefined.foo` の例外になり、「旧セーブだけ壊れる」＝開発中は再現しない厄介なバグになる（戦国風雲記 ターン終了バグ PR #289 で実証）。
- **実装要件**:
  - **読み込み時に一度だけ正規化層を通す**: 永続データを読んだ直後に `normalizeState(state)` を1本置き、①マスタに増えた項目を既定値で補完（既存値は絶対に触らない）②実体の無くなったID参照を除去③数値の `NaN` / 型崩れを是正、をまとめて行う。以後の計算コードは「欠損は無い」前提で書けるようになり、防御コードの散在を防げる。
  - **正規化はマスタが変わりうる全ての入口で呼ぶ**: 読み込み時だけでなく、ユーザー編集（項目の削除・所有者変更等）を反映した直後にも通すこと。入口が1つ漏れると、そこを経由した時だけ壊れる。
  - **「後から追加された項目」は"未登場"の既定値で補う**: 過去のセーブにその項目は元々存在しなかったので、有効な状態（生存・所有済み等）で足すと履歴の辻褄が合わない。`alive:false` / `owner:null` のような不参加の既定値を使う。
  - **最下層のアクセサを欠損に耐えさせる**: 正規化を入れてもマスタ更新のタイミング差で漏れは起きる。`daimyoOf()` のような基礎アクセサは `find()` の結果が `undefined` でも空配列を返す等、**そこで例外を投げない**設計にしておくと、欠損が致命傷ではなく軽微な表示崩れで済む。
  - **検証は"旧セーブ相当"を合成して行う**: 実際に古いセーブを持っていなくても、正常なセーブから要素を意図的に削った/壊したケース（項目欠落・ID参照だけ残存・`NaN` 混入・編集後の状態）を並べて、全ケースで処理が完走することをヘッドレスブラウザで確認する。あわせて修正前のコードで**そのケースが再現すること**も確認し、テストが空振りでないことを担保する。

## Skill: 多段の状態更新はトランザクション化する (Transactional State Updates)
- **概要**: 「収入計上 → AI思考 → 確定」のように状態を直接書き換えながら進む多段処理は、途中で例外が出ると**前半の副作用だけが残った半端な状態**になる。ユーザーが再試行するたびに前半が再実行され、状態が単調に悪化していく（戦国風雲記「ターン終了を押すたび金銭だけ増える」PR #289 で実証）。
- **実装要件**:
  - **スナップショット → 実行 → 失敗時ロールバック**の構造にすること。処理前に状態を複製（`structuredClone` 等）し、`try` の中で全段を実行、`catch` で複製を書き戻す。これで再試行が冪等になり、障害の原因が残っていても状態は汚れない。
  - **途中で確定した処理を二重実行しない**: ロールバックでなく「途中から再開」を選ぶ場合は、完了済みの段（収入計上等）をフラグで記録し、再開時にスキップすること。ロールバックと再開のどちらを採るかは段ごとに決め、両方を曖昧に混ぜない。
  - **副作用の順序を「計算 → 一括反映」に寄せる**: 各段が状態を直書きする設計そのものが原因なので、可能なら全段を純粋計算にして最後にまとめて反映する。ロールバックは既存構造を壊さずに済ませるための現実解であって、理想形ではない。

## Skill: パフォーマンス最適化 (Performance Optimization)
- **概要**: ゲームループや重いCanvas描画でも60fps を維持するための手法。
- **実装要件**:
  - アニメーションループは必ず `requestAnimationFrame` を使い、`setInterval` / `setTimeout` による描画ループを禁止する。
  - オブジェクト生成（`new`, 配列リテラル等）をループ内で繰り返さず、オブジェクトプールパターンを採用すること。
  - Canvas の `clearRect` は全画面クリアではなく、変化した領域のみをダーティレクト（Dirty Rect）でクリアすることを検討する。
  - 変化しない背景レイヤーはオフスクリーンCanvas（`document.createElement('canvas')`）に事前描画してキャッシュすること。
  - `ctx.save()` / `ctx.restore()` のネストは最小限にし、状態変更はまとめて行うこと。
- **静的レイヤーの3大キャッシュパターン**（戦国の野望 Cycle1〜9 で実証。マップ ~7.5→35fps超 / 戦闘 ~19.3→36fps）:
  - **レイアウトのメモ化**: カメラ変換（ズーム/パン）はctx側が担うため、ワールド座標系で計算するレイアウト（ラベル配置等）はカメラ操作では不変。毎フレーム再計算せず、入力（所有・選択・ターン等）の変化検知でメモ化する。取りこぼし対策に0.5秒程度の安全リフレッシュを併設すると自己修復する。編集/ドラッグ中はメモ化を迂回する。
  - **オフスクリーン合成→ブリット**: 時間非依存で毎フレーム同一の合成結果（背景グラデ＋大判画像、タイルマップの地形等）はワールド解像度のオフスクリーンへ一度合成し、以降はブリットのみ。静的層と動的層の分割点は「フレーム間で変わる最初の要素」に置く（描画順を壊さない）。依存アセットが遅延ロードなら暫定構築→到着後に一度だけ再構築。
  - **静止検知のスクリーン座標二次キャッシュ**: ワールド解像度オフスクリーンでも、毎フレームのカメラ変換つきブリット（拡縮リサンプリング）自体が支配的コストになり得る（実測+18fps級）。カメラキー（zoom|cx|cy）が前フレームと一致＝静止なら一度だけスクリーン解像度へ変換結果を焼き、以降は等倍コピー1回。キー不一致（移動/ズーム中）は従来ライブ経路のままにすれば移動時の性能・見た目の回帰がゼロで済む。
- **やってはいけない**: カメラのズーム変換配下で描画されるベクター要素（グラデ・パス描画）のビットマップキャッシュ。高ズームで拡大されてボケる（ライブ描画はズーム後解像度で再ラスタライズされ鮮明）。キャッシュはカメラ変換の外側（ワールド解像度で完結する層）に限る。**例外**: サイズクランプ等で要素の画面上サイズに上限がある場合は、上限以上の固定解像度スプライトなら拡大が起きずボケない（クランプ導入がビットマップ化を解禁する。戦国の野望Cycle7の家紋スプライトで実証）。なお `shadowBlur`/`shadowOffset` はctx変換の影響を受けないデバイス座標系のため、焼き込み時は比例値へ換算して見た目を合わせる。
- **前処理コストは「毎フレーム／静止のたび／ロード時に一度」のどこに置くか**（戦国風雲記 地図フリーズの3連続手戻りで実証。PR #273→#274→#275）:
  - 重い前処理（畳み込みフィルタ＝アンシャープマスク等）を**カメラ静止のたびに全域へ焼く**設計は、体感上ワーストの配置になる。パン/ズームを止めるたび・画面へ入るたびに1フレーム 1.5〜3.4秒のフリーズとして出るため、平均FPSには現れず「なんとなく重い」と報告される。静止時ベイクに置いてよいのは**変換のみの軽い焼き直し**（スクリーン座標二次キャッシュ）で、生成コストが数十ms以上ある処理は**ロード時に一度だけ**へ移すこと。
  - 軽量化で画質が落ちたときの正解は「品質を諦める」ではなく**高品質な中間ビットマップをロード時に一度だけ作る**こと（例: 高品質補間で2倍プリスケールした `mapSharp` を作り、毎フレームはそこから拡大するだけ）。生成一度きり約35msで、毎フレーム高品質ベイク相当の見た目をコストほぼゼロで再現できる。プリスケール倍率はメモリと引き換え（2倍≈25MB / 3倍≈57MB）なので、選んだ倍率と却下した倍率の理由をコード内コメントに残す。
  - **補償ハックは原因を直したら撤去する**: 拡大ぼけを誤魔化すために足した装飾（微細グレイン等）は、上流の解像度・補間を改善した時点で不要になるだけでなく、高倍率で**ノイズとして害になる**。品質改善を入れたら「その品質不足を補うために過去入れた小細工」を検索して外すまでが1セットと考える。
- **カリングの位置づけ**: 可視矩形AABBカリングは疎なビュー/画面端で効く安全策。高ズームで密集地に寄ると可視要素の拡大描画でラスタライズ面積が増え、枚数減が相殺されてFPSは横ばい（回帰はしない）。主対策ではなく補助と考える。
