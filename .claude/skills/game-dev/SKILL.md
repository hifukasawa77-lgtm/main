# ゲーム開発スキル集

Canvas API のみで構築するトップビュー / パズル系ゲームの実装ガイドライン。

---

## Skill: 衝突判定 (Collision Detection)
- **概要**: Canvas ゲームで多用する衝突判定パターンをケース別に使い分ける。
- **実装要件**:
  - **矩形同士 (AABB)**: `x1 < x2+w2 && x1+w1 > x2 && y1 < y2+h2 && y1+h1 > y2` で判定。最も軽量なので壁・床・アイテムに優先使用すること。
  - **円同士**: 2点間の距離 `Math.hypot(dx, dy)` が半径の和未満なら衝突。キャラクター同士や弾丸の判定に使用すること。
  - **矩形×円**: 矩形上の最近接点を求め、円の中心との距離で判定する。複合形状のヒットボックスに使用すること。
  - 判定頻度が高い場合は空間分割（グリッド / クアッドツリー）を導入し、総当たりを避けること。

## Skill: キャラクターAIパターン (Character AI Patterns)
- **概要**: 敵キャラクターやNPCの動作を状態機械で管理する。
- **実装要件**:
  - AIの状態は `{ state: 'idle' | 'patrol' | 'chase' | 'attack' | 'dead' }` のように文字列で明示的に管理すること。
  - 各状態の遷移条件をコメントで明記し、`update()` 内で `switch(this.state)` を使って処理を分岐すること。
  - **パトロール**: ウェイポイント配列を順に移動。端に達したら折り返すか循環させる。
  - **追跡**: プレイヤーとの角度を `Math.atan2(dy, dx)` で算出し、その方向へ一定速度で移動する。
  - **視野判定**: プレイヤーとの距離＋角度（内積）で扇形の視野範囲内かどうかを判定すること。

## Skill: ゲームループ設計 (Game Loop Design)
- **概要**: 入力 → 更新 → 描画のサイクルを安定して60fps で動作させる。
- **実装要件**:
  - デルタタイム (`deltaTime = (timestamp - lastTimestamp) / 1000`) を毎フレーム計算し、移動量を `speed * deltaTime` で算出することでフレームレート非依存にすること。
  - ループは `update(deltaTime)` と `draw()` を明確に分離し、描画ロジックに状態変更を混入させないこと。
  - `deltaTime` の上限を `Math.min(deltaTime, 0.1)` でキャップし、タブ非アクティブ復帰時の大ジャンプを防ぐこと。
  - ゲームの一時停止は `cancelAnimationFrame` ではなくフラグ (`isPaused`) で制御し、ループ自体は維持すること。

## Skill: Canvas API テクニック拡充 (Advanced Canvas Techniques)
- **概要**: 既存の有機的描画・グラデーション・エフェクトスキルを補完する高度なテクニック。
- **実装要件**:
  - **スプライトシート描画**: `drawImage(img, sx, sy, sw, sh, dx, dy, dw, dh)` の9引数形式でアニメーションフレームを切り出すこと。
  - **ピクセル操作**: `getImageData` / `putImageData` は重いため、エフェクト用途に限定し毎フレーム呼び出しを禁止する。
  - **クリッピング**: `ctx.clip()` でキャラクターの描画範囲をマスクし、ウィンドウ外へのはみ出しを防ぐこと。
  - **文字描画**: HUDのテキストは `ctx.textBaseline = 'top'` を統一設定し、`measureText` で幅を取得してセンタリングすること。

## Skill: グリッド×背景アート整合と到達性の機械検証 (Grid/Art Alignment & Reachability Verification)
- **概要**: 固定グリッド（ヘックス/タイル）レイアウトと背景グラフィックの整合、および通行判定の妥当性は目視でなく機械的に検証する（sengoku.html 攻城戦ヘックス修正で実証）。
- **実装要件**:
  - **座標変換を再現したオーバーレイ検証**: グリッドと背景絵の整合確認・トレースは、描画コードの座標変換（カバー画像フィット・セル中心算出等）を検証スクリプト側で再現し、背景画像へグリッドを機械的に重ね描きして行うこと。目視のスクリーンショット比較は不正確なので判定に使わない。背景のズーム/拡縮は座標ずれの原因になるため、グリッドを重ねる層は等倍固定を基本とする。
  - **通行判定はグラフBFSで両側検証**: 通行レイアウトを変更したら、①障害物（門・壁）破壊込みで目標へ到達可能、②無傷なら封鎖されている、の**両方**をBFSで機械検証すること。ヘックスは斜め方向の隣接があり、目視の「壁が連なって見える」では隙間を見落とす。あわせてスポーン/配置マスの確保と非重複も検証する。
  - **HUD凡例と描画コードの照合**: 凡例文字列は描画分岐と乖離しうる（未使用セル種の名残等）。凡例は描画コードの分岐（色・種別）から機械的に照合できる形で保守し、レイアウト変更時に必ず突き合わせること。
  - **画像トレース地形の遠近は縦位置（行）で補正**: 背景画像の色/テクスチャ解析では平地の「遠景/手前」を判別できない。頼れる信号は行インデックス（縦位置）のみ。前線・初期配置の行には下限行（例: FRONT_MIN）を噛ませ、上部行で完結する水域・山岳帯は遠景として戦場外/装飾へ降格すること。トレース分類に依存しきらない（sengoku.html 野戦の「敵が地平線に浮く」不具合で実証）。
  - **AI自動指揮の計測は勝率でなく勝ち筋(reason)別に集計**: 勝率だけでは「たまに勝つ」に紛れて「意図した勝利条件を一度も達成できていない」質的欠陥を見逃す。決着理由別に集計し、あわせて到達性BFSで「そもそも詰みか」を切り分けると、AIの弱さ（パラメータ調整で対応）と設計バグ（コード修正が必要）を区別できる（sengoku.html 委任攻城AIで実証: 勝率6/24かつ天守制圧ゼロ→目標固定＋ラウンド延長で19/24）。

## Skill: 固定Canvas UIのモバイル可読性対策 (Fixed-Canvas Mobile UI Readability)
- **概要**: 固定解像度のcanvasをCSSで画面いっぱいに引き伸ばす方式は、スマホで文字・ボタンが縮んで読めなくなる。部分的な文字だけの拡大はレイアウト破綻（枠あふれ・重なり）を招く（sengoku.html スマホメニュー改善で実証）。
- **実装要件**:
  - **パネルごと拡大＋入力逆変換**: タッチ環境ではオーバーレイ/パネル全体を画面中心基準の相似変換で一括拡大する（暗幕は等倍で先に描く）。タップ座標は `pa = center + (p - center) / s` の逆変換で命中を担保する。既存のボタン個別スケール機構は描画中フラグで無効化し、二重拡大によるはみ出しを防ぐこと。
  - **文字あふれの最終防衛線はラベル横幅フィット**: ボタン描画の共通処理に「`measureText` でラベル幅がボタン幅を超えるなら自動縮小」を1箇所入れる。翻訳・可変数値・スケール差の全てを吸収でき、パネル拡大や個別サイズ調整より保守が楽。
  - **タッチ環境はPlaywrightで pointer:coarse を強制して再現**: `addInitScript` で `pointer: coarse` を強制し、実機相当の横向きビューポート（例: 852x393）で「はみ出しゼロ」を確認する。PC（非タッチ）は等倍維持の非退行も併せて検証すること。
  - **オーバーレイ表示中は固定HTML UIを隠す**: canvas外に固定配置したHTMLボタン（全画面/BGM/遊び方等）は、Canvas側のパネル・オーバーレイに被ると「タブを押したつもりが全画面解除を誤タップ→画面が固まったように見える」事故を生む。パネル/オーバーレイの表示中は固定HTML UIを一括で非表示にすること（z-index調整では指の当たり判定が残るため隠す）。
  - **タッチではホバー前提のUIを無効化する**: マウスのホバー追従（カーソル位置に情報カードを出す等）はタッチだとタップ＝ホバー扱いになり、「何もない所を触っただけで情報が出る」誤作動になる。タッチ環境では追従を切り、情報表示はマーカー等の**明示的な当たり判定にヒットした時だけ**に限定する（ヒットしない領域のタップは無反応が正しい）。

## Skill: Canvas絶対座標レイアウトの整合 (Absolute-Coordinate Layout Consistency)
- **概要**: Canvasにはレイアウトエンジンが無く、要素は互いを押しのけない。ある要素の座標・寸法を変えても他要素は再配置されないため、「片側だけ更新」が即座に重なり・はみ出しとして出る（戦国風雲記 拝領/処分モーダルの肖像重なり PR #281、スマホ城配置崩れ PR #279 で実証）。
- **実装要件**:
  - **条件分岐でレイアウトが変わるなら、同じパネル内の全要素の座標を同じ条件で見直す**: `py+(img?400:140)` のような三項演算子でパネル内要素を出し分けている箇所は、片方の分岐だけ座標を変更すると他方が重なる典型パターン。肖像の有無・翻訳文の有無・ボタン数などで分岐したら、その分岐に属する**全要素**の座標を洗い出して更新すること。検証は分岐の全組み合わせ（肖像あり/なし × 拝領/処分 等）でスクリーンショットを撮って行う。
  - **衝突回避レイアウトの占有矩形は「実際の描画寸法」で予約する**: レイアウト計算が1倍サイズで矩形を予約し、描画側が拡大率（例: モバイル用 `MK=1.3`）を掛けていると、膨らんだラベル/アイコンが隣接要素へ重なる。予約矩形はアンカー基準で描画倍率を掛けて計算すること。**描画に掛かる倍率とレイアウト計算に掛かる倍率が一致しているかは、拡大率を導入した時点で必ず確認する**（PCは倍率1で無症状のまま、モバイルでだけ「配置がめちゃくちゃ」に見えるので発見が遅れる）。
  - ワールド座標（`nx` 等）は等倍のまま保持し、拡大は描画側の `ctx.scale` と占有矩形の計算に反映する。座標データ自体を倍率で書き換えると、倍率が変わるたびにデータが壊れる。

## Skill: 設計キャンバスを正としたジオメトリ導出 (Design-Canvas Geometry)
- **概要**: キャンバスの解像度・アスペクト比を変えると、そこから導出されるべき盤面・トレース済みレイアウト・UI配置が**別の場所に絶対値で焼き込まれたまま**取り残される。画面外へ落ちたヘックスや部隊は例外も警告も出さず、静かにゲームプレイを壊す（sengoku.html 攻城戦で 2560x2080→2560x1440 に変えた際、攻め手の全部隊が4日間不可視だった実績）。
- **実装要件**:
  - **レイアウトをトレース／調整したときの寸法を `*_DESIGN`（設計キャンバス）として定数に残し、実キャンバスへは contain フィット**（`FIT = min(W/w, H/h)`）して幾何を導出すること。盤面を等倍で置き直すのではなく設計キャンバスごと縮めれば「背景画像上のどこにどのマスが載るか」の対応が保たれる。生成側スクリプト（トレースツール等）にも「ここは設計キャンバスであり実装側の `*_DESIGN` と同値に保つ」旨を明記する。
  - **設計値で調整済みの重ね描き（文字・耐久バー・エフェクト）にも同じ係数を掛ける**こと（`px(v) = v * FIT`）。掛け忘れると駒より文字が大きくなって隣のマスへはみ出す。
  - **`W`/`H` を変える変更では「W/H から導出されるべき値が定数で書かれていないか」を横串で洗う**。固定グリッドは画面外へ出ても無症状なので、検証は「盤面矩形が画面内か」「画面外に落ちたユニット数が0か」「ボタン矩形と盤面矩形が重なっていないか」を機械判定にすること（目視では下端の欠けに気づきにくい）。

## Skill: 姉妹ファイル間でのデータ生成スクリプト複製は消費側も突き合わせる (Cross-File Data Reuse Verification)
- **概要**: GameKit系のゲーム（genpei/taihei/sengoku/sanguo等）は座標データ生成スクリプトを姉妹ファイルから複製して作ることが多い。生成側のJSONコメントに座標系が明記されていても、複製先の消費側コード（描画・当たり判定）が同じ座標系を前提にしているとは限らない（taihei.html で`provinces.json`の`x`/`y`を「論理座標(0..1000 x 0..650、位相のみ)」と明記していたのに、`provScreenXY`が絵地図の画素座標として直接スケールし、国マーカーが地図の左上へ固まった実例）。
- **実装要件**:
  - データ生成スクリプトを姉妹ファイルから複製したら、**複製元（例: genpei.html）の対応する描画コードが実際にどのフィールドをどう使っているか**を必ず突き合わせる。コメントの記述だけを信じない。
  - 複製元が座標系変換済みの別フィールド（キャリブレーション済みの`mx`/`my`等）を経由している場合、複製先も同じフィールドを使うこと。論理座標を画素座標として流用するショートカットは取らない。
  - 修正時は「無ければ旧来のフィールドへフォールバック」を残すと、揃っていないデータが残っていても検出せず沈黙して壊れたままになる。全件がキャリブレーション済みフィールドを持つことを機械検証すること。

## Skill: 対称ゲームの判定は陣営の絶対基準で書く (Absolute-Side Invariants)
- **概要**: プレイヤーが攻/防どちらの陣営にもなり得る対称ゲームでは、勝敗・占拠等の判定を「プレイヤー相対」で書くと片側の陣営でだけ壊れる（sengoku.html 防衛攻城戦の開幕即敗北バグで実証）。
- **実装要件**:
  - 勝敗・占拠・制圧の判定は `occ.side === 'atk'` のような**陣営の絶対基準（不変条件）**で書くこと。`occ.side === this.playerSide` のようなプレイヤー相対基準は、描画（絶対基準）と判定（相対基準）の乖離を生み、プレイヤーが逆陣営を選んだ時だけ壊れる。
  - **派生フラグは単一のソースから導出**すること。`this.siege = battleType==='siege' || 城Lv>=3` のように「明示選択」と「旧来の推定条件」をORで残すと、描画は `battleType` 基準・ロジックは `this.siege` 基準で乖離し、「森に入れない」「敵配置がおかしい」等の間接症状として現れて原因特定が遠回りになる。描画とロジックで同じ判定を使うこと。
