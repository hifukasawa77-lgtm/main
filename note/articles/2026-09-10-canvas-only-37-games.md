ブラウザゲームを37本<!--fact:games-->公開しました。全部ひとりで、
**フレームワークもビルドツールも使っていません。**

素の HTML と CSS と JavaScript、描画は Canvas API だけ。
`npm run build` は一度も走らせていません。`git push` すると GitHub Pages に出ます。
それだけです。

将棋・囲碁・チェス・麻雀・花札のようなボードゲームAIから、
トップビューRPG、ベルトスクロールアクション、戦国シミュレーション、
Web Audio のシンセサイザーまで、同じ作り方で作りました。

この記事は「フレームワークを使うな」という話ではありません。
**37本作ってみて、何が本当に省けて、何は結局自分で書くことになったのか**の記録です。

## 省けたもの

### 1. 環境構築の時間がまるごと消える

新しいゲームを作り始めるときにやることが、**HTMLファイルを1枚コピーするだけ**になります。

依存関係がゼロなので、`npm install` が失敗しません。
Node のバージョンが上がって動かなくなりません。
2年前に書いたゲームが、今日そのまま開いて動きます。
**これは思っていたよりずっと大きい効果でした。**

個人開発で一番よく死ぬのは、モチベーションが切れることではなく、
**久しぶりに開いたら環境が壊れていて、直すのに1日かかること**です。
その1日が発生しないと、作りかけのものに戻れます。

### 2. デプロイという工程が消える

ビルド成果物が無いので、リポジトリの中身がそのまま公開物です。
「手元では動くのに本番で動かない」が原理的に起きません。
本番の確認は公開URLを開くだけです。

### 3. 依存パッケージの脆弱性対応が消える

これは想定していなかった副産物です。
依存が無いので、脆弱性の通知が来ません。対応する作業が発生しません。
個人開発の可処分時間は週に数時間しかないので、
**作業が「発生しない」ことの価値は、作業が「速い」ことより大きい**と実感しました。

## 省けなかったもの

正直に書くと、**フレームワークが持っていた仕事の大半は、結局自分で書くことになりました。**

3本目くらいまでは「素で書けるじゃないか」と思っていました。
7本目あたりで、同じコードを毎回コピペしていることに気づきます。

- ゲームループ（`requestAnimationFrame` とデルタタイム）
- キー入力とタッチ入力の抽象化
- 矩形と円の衝突判定
- 効果音（Web Audio のオシレータ）
- パーティクル
- セーブデータ（localStorage の読み書きと世代管理）
- UI（ボタン、パネル、モーダル）

これを毎回書くのは無理です。かといって、ここでフレームワークを入れると
上で書いた3つの利点が全部消えます。

そこで **GameKit** という自作のマイクロエンジンを1枚のJSファイルに切り出しました
（`gamekit/gamekit.js`）。CDNもビルドも要らず、`<script>` で読むだけのものです。
新規ゲームは `gamekit/template.html` をコピーして始めます。

**つまり結論は「フレームワークは要らない」ではなく、
「自分の作るものの範囲に合わせた薄い層を、自分で持つ」でした。**
汎用フレームワークが重いのは、自分が作らないものまで面倒を見ているからです。

## 実際に効いた3つの技法

### デルタタイムでフレームレート非依存にする

`requestAnimationFrame` は60fpsで呼ばれるとは限りません。
144Hzのモニタでは倍速になり、重い場面では半分になります。

```js
let last = performance.now();
function loop(now) {
  const dt = Math.min((now - last) / 1000, 0.05);  // 秒。タブ復帰時の巨大値を上限で潰す
  last = now;
  update(dt);   // 移動は速度×dt で書く
  draw();
  requestAnimationFrame(loop);
}
```

`Math.min` の上限が要点です。
タブを裏に回して戻すと `dt` が数秒になり、**キャラクターが壁を貫通します。**

### オブジェクトプールでGCを止める

弾幕やパーティクルで毎フレーム `new` すると、GCが走った瞬間にカクつきます。
使い終わったオブジェクトを配列に返して使い回すだけで、この揺れは消えます。

### オフスクリーンCanvasに焼く

背景やタイルマップのように**毎フレーム変わらないもの**は、
別の Canvas に一度だけ描いて、本番では `drawImage` で1回貼るだけにします。
タイルを毎フレーム数百回描くのと、画像を1枚貼るのとでは、当然ながら桁が違います。

ただしこれは**罠でもあります。** 焼くコスト自体が重いので、
「静止した瞬間に焼く」ような実装にすると、**止まるたびに一瞬固まる**ようになります。
前処理は「変化したときに1回」であって「静止したときに毎回」ではありません。
私はこれを一度やって、原因を描画側だと誤診しました。

## 一番痛かった失敗: リポジトリが1.6GBになった

37本もあると、画像アセットが積み上がります。全部PNGで置いていました。

**GitHub Pages の公開サイトには1GBの上限があります。** 超えました。

WebP へ再エンコードして 264MB まで落として解決……したのですが、
**再エンコードした瞬間、いくつかのゲームで絵が無言で消えました。**

原因は `drawImage` の切り出し矩形（source-rect）を画素値で直書きしていたことです。

```js
// 1254px の画像から切り出す前提で書かれていた
ctx.drawImage(img, 900, 300, 128, 128, x, y, 64, 64);
```

画像を 256px に縮めると、この矩形は画像の外を指します。
**外を指した drawImage は、例外を投げません。何も描かずに黙って成功します。**
404も出ません。コンソールは綺麗なままで、絵だけが消えます。

これに懲りて、私は「絵が実際に描かれたか」を機械で確かめる検査を書きました
（`scripts/verify-game-assets.mjs`、`scripts/verify-asset-format.mjs`）。
アセットを触ったら必ず通します。

そして本当の教訓はこちらでした。

> **CLAUDE.md に「WebPで置くこと」と書いてあっても、守られているかを確かめる手段が無ければ、
> 誰も気づかないまま元に戻ります。**

実際、一度WebP化した3週間後にPNGが235枚戻っていて、容量は587MBまで膨らんでいました。
方針を書いた本人（私です）が気づいていませんでした。
いまは検査スクリプトが未追跡ファイルまで見ていて、方針から外れた画像があると落ちます。

## ボードゲームAIも同じ枠でいけた

「Canvasで作れるのは動きもののゲームだけでは」と思われがちですが、
将棋・囲碁・チェス・麻雀・花札・オセロ・バックギャモンも同じ作り方で入りました。
描画がほぼ静止画になるぶん、こちらはむしろ**思考ルーチンだけの勝負**になります。

使った探索は、ゲームによって変えています。

- **チェス・オセロ**: ミニマックス＋アルファベータ枝刈り。評価関数は駒得と位置価値の重み付け
- **囲碁**: UCT-MCTS（モンテカルロ木探索）。9路盤と13路盤。
  囲碁は評価関数を書けないので、最後まで打ち切ってしまう方が早い
- **将棋**: 駒割り＋利きの評価に、終盤だけ読みを深くする可変深さ

ここで効いたのが、**探索をメインスレッドで回さないこと**です。
素直に書くと、AIが考えている数秒間、画面が固まって操作を一切受け付けなくなります。
`setTimeout(fn, 0)` で探索を分割して、フレームの合間に少しずつ進めるようにすると、
「AIが考え中」のアニメーションを出しながら待たせられます。

**これは「速くする」最適化ではありません。同じ時間かかっても、
画面が動いていれば人は待てる**、という体感の問題です。
実測のFPSより、こちらの方がプレイ感に効きました。

## スマホ対応で毎回つまずいたこと

37本のうち大半はスマホでも遊べるようにしてありますが、
Canvasゲームのモバイル対応には、HTMLのUIには無い落とし穴があります。

**Canvasは固定サイズで作ると、スマホで文字が読めなくなります。**
1280×720で作ったUIを画面幅に合わせて縮めると、そのままフォントも縮みます。
かといってCanvas自体を拡大すると、今度は**タップ座標がずれます。**

解決は、描画倍率と入力の逆変換を必ず対にすることでした。

```js
// 画面に合わせた倍率
const scale = Math.min(cv.clientWidth / BASE_W, cv.clientHeight / BASE_H);
// 入力は必ず逆変換して基準座標へ戻す
function toGame(e) {
  const r = cv.getBoundingClientRect();
  return { x: (e.clientX - r.left) / scale, y: (e.clientY - r.top) / scale };
}
```

片方だけ直すと、**見た目は正しいのにボタンが押せない**という状態になります。
しかもこれは例外を出しません。「押しても何も起きない」だけです。
私は最初、原因をイベントの登録漏れだと思って別の場所を探し続けました。

## 37本作った今の結論

- **フレームワークを使わない選択の価値は、速さではなく「作業が発生しないこと」にある**
- **ただしフレームワークの仕事は消えない。自分の範囲に合わせた薄い層として持ち直すことになる**
- **Canvas は例外を出さずに黙って失敗する。目視レビューでは絶対に見つからない**

最後の1点が、実は一番時間を吸いました。
「例外もエラーも出ないのに、絵だけがずれる・消える」バグを何度も踏んでいて、
その都度どんな検査を書いて再発を止めたかは、別の記事にまとめています。
