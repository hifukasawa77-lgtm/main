「起動して例外が出ないか」を確認する検査は、**タイトル画面が出た瞬間に満足してしまいます。**
ゲームとして最後まで遊べるかどうかは、別の話です。

幕末シミュレーションのあるボタンを押した瞬間、画面が例外もエラーも出さずに
固まる不具合がありました。見つけたのは目視でも既存の検査でもなく、
**キーとクリックを無作為に浴びせ続けるツール**です。

## この記事で分かること

- タイトルも地図も無事に表示されるのに、特定の操作をした瞬間だけ固まるバグの正体
- `MutationObserver`で監視対象のDOMを書き換えるときに踏みやすい罠
- 「起動して例外が無いか」では見つからない不具合を探すための、無作為入力ツールの作り
- 固まったページをどう検出するか（固まると、終了処理そのものも返ってこない）

## 先に結論

- **`MutationObserver`のコールバックの中で、観測対象のDOMへ値を書き込むときは、
  「変わるときだけ」書く。** 同じ値の代入でも子ノードは置き換わり、変更として
  通知される。ガードを入れないと、コールバックが自分自身を呼び直し続ける
- **「起動して例外0件」の検査は、この種の不具合を素通りする。** タイトルも地図も
  無事に表示され、固まるのは特定のボタンを押した瞬間だけだからだ
- **無作為な入力を浴びせるツールは、キー入力とクリックの比率・座標の範囲・
  画面の「指紋」の取り方まで具体的な設計が要る。** 盤面をDOMで描くゲームと
  Canvasで描くゲームでは、画面が変わったかどうかの判定方法自体が違う
- **固まったページは、終了処理の呼び出しすら返ってこない。** 検出には
  タイムアウト付きで「待たずに見切る」仕組みが必要になる

## 1. 同じ値の代入でも、DOMの変更通知は飛ぶ

幕末シミュレーションには、初めてのプレイヤー向けに操作を案内するスクリプト
（`bakumatsu-guide.js`）があります。これは`document.body`の子孫を
`MutationObserver`で監視し、特定のボタンが出てきたら案内文を書き換えるという
作りです。

このスクリプトは、監視しているDOM自身を書き換えるコードです。
ここで気をつけるべきことは、**代入する値が直前と同じでも、
DOMへの書き込みそのものは「変更」として`MutationObserver`に通知される**
ということです。

案内スクリプトが監視コールバックの中で無条件に`textContent`や`innerHTML`へ
代入していた場合、代入のたびに変更通知が飛び、通知を受けたコールバックが
また同じ代入を行い、また通知が飛ぶ……という形で**コールバックが自分自身を
呼び直し続けるループ**になります。これは例外を一切出しません。ブラウザの
タブはただ固まったように見えるだけです。

現在のコードには、この問題への対策がそのまま残っています。代入の前に
必ず現在の値と比較し、**変わるときだけ書く**という形です。

```js
// 代入前に現在値と比べる。同じ値を無条件に書き込むと、MutationObserver が
// 「変更された」と通知を出し続け、コールバックが自分自身を呼び直すループになる
if (b.textContent !== '⚔ 戦の準備をする') b.textContent = '⚔ 戦の準備をする';
// ...
if (h.textContent !== t) h.textContent = t;
// ...
if (q.innerHTML !== qt) q.innerHTML = qt;
```

観測対象が`{childList: true, subtree: true}`、つまり子要素の追加・削除まで
見ている設定だと、`textContent`や`innerHTML`への代入は中の子ノードを
作り直す操作になるため、これも変更として検出されます。値が同じだから
安全、とはいきません。

## 2. 起動検査は、タイトルも地図も無事に表示するので素通りする

この種の不具合が厄介なのは、**起動して例外が出ないかを確認する検査が
普通に合格してしまう**ことです。タイトル画面は問題なく表示されますし、
マップ画面も正常に描かれます。固まるのは、プレイヤーが敵地を選んで
「戦の準備をする」を押すという、**特定の操作の組み合わせをした瞬間だけ**です。

「起動して例外0件」を見る検査は、この経路を通らないので、
何も異常を報告しません。実際にこの不具合を見つけたのは、
目視のプレイテストでも既存の起動検査でもなく、**無作為な入力を
延々と送り続けるツール**でした。

## 3. 無作為入力ツールの作り — キー8割・クリック2割、画面の「指紋」で判定

このツール（`scripts/playtest-fuzz.mjs`）は、ページを開いたあと
種付きの疑似乱数でキー入力とクリックを交互に送り続け、画面が
**応答し続けているか**・**入力に反応しているか**・**例外が出ていないか**
の3点を確認します。

乱数は種（シード）付きです。既定値は固定されていて、同じ種を指定すれば
同じ入力列が再現されるため、**落ちたときに同じ手順で再現できます。**

```js
const rng = (seed) => { let s = seed >>> 0; return () => ((s = (s * 1664525 + 1013904223) >>> 0) / 2 ** 32); };
// 8割はキー入力、2割は画面内の無作為な座標へのクリック
if (random() < 0.8) {
  const key = KEYS[Math.floor(random() * KEYS.length)];
  input = page.keyboard.press(key, { delay: 15 });
} else {
  const x = Math.round(40 + random() * 1200), y = Math.round(40 + random() * 720);
  input = page.mouse.click(x, y);
}
```

画面が実際に変化したかどうかは、**一番大きいCanvasを24×24へ縮小した
標本画素と、DOM構造の両方**を合わせた「指紋」で判定します。

```js
// 画面の指紋: 一番大きいキャンバスの標本画素＋DOM構造の標本。変わったかどうかだけを見る
const canvases = [...document.querySelectorAll('canvas')].filter((c) => c.width > 0 && c.height > 0);
canvases.sort((a, b) => b.width * b.height - a.width * a.height);
const canvas = canvases[0];
// 盤面をDOMで描くゲーム（将棋など）は、キャンバスも本文も変わらず、クラス・属性だけが変わる。構造ごと見る
```

Canvasの画素だけを見ると、盤面をDOM要素（`<div>`やテーブル）で描く
将棋・囲碁のようなゲームでは、盤面が動いてもCanvasの中身が変わらないため
「入力が効いていない」と誤判定されます。DOM構造も合わせて見ることで、
描画方式が違うゲームも同じ基準で判定できます。

## 4. 固まったページは、終了処理も返ってこない

固まったタブを検出するとき、単純に「結果を待つ」コードを書くと、
固まったページの検出そのものが固まってしまいます。送った入力への応答も、
ページを閉じる操作も、固まったページからは一切返ってきません。

対策は、全ての待ち受けをタイムアウト付きの競争にすることです。

```js
// 固まったページは入力の送信そのものが返ってこない。時間で見切る（返らなければ null）
const within = (work, ms) => Promise.race([work, new Promise((resolve) => setTimeout(() => resolve(null), ms))]);
```

入力を送ってからの応答待ちも、ページを閉じる処理も、すべてこの`within`を
経由させています。タイムアウト（3秒）を超えて応答が無ければ「固まった」と
判定し、閉じる処理自体も待たずに次へ進みます。**固まったものを律儀に
待っていると、検査そのものが永久に終わらなくなる**ためです。

## 5. 「反応している」と「ちゃんと変化している」も別に見る

無作為入力ツールが報告するのは「固まっていないか」と「入力に反応しているか」の
2つです。後者は、送った入力の回数に対して画面の指紋が何通り観測されたかで判定します。

```js
check(`${label}: 入力に画面が反応する`, hung || seen.size > 1,
  !hung && seen.size <= 1 ? '最初から最後まで画面が同じ（入力が死んでいる／ソフトロック）' : `画面の状態 ${seen.size} 通り`);
```

固まっていないのに画面の指紋が常に1種類しかない場合は、**入力そのものが
効いていない**ことを意味します。無限ループで固まる不具合とは別の壊れ方
（ボタンへのイベント登録漏れなど）も、この仕組みで同じ検査から見つかります。
対象になるのは、画面にCanvasか操作できる要素（ボタン・クリック可能な要素・
リンク）のどちらかがあるページだけに絞ってあります。静止した説明ページを
延々とクリックしても、何も分かりません。

## まとめ

- **`MutationObserver`のコールバックが観測対象のDOMを書き換えるなら、
  同じ値への代入でも「変わるときだけ書く」ガードを入れる。** 無条件の代入は
  コールバックの自己再帰を生み、例外を出さずに画面を固める
- **「起動して例外が無いか」の検査は、特定の操作の組み合わせでしか起きない
  不具合を素通りする。** タイトルも地図も無事に表示される
- **無作為入力ツールは、入力の比率・座標の範囲・画面変化の判定方法を
  具体的に設計する必要がある。** Canvas描画とDOM描画のゲームでは、
  画面が変わったかどうかの見方自体が違う
- **固まったページは、終了処理すら返ってこない。** 検出は全ての待ち受けを
  タイムアウト付きにし、待たずに見切る設計にする
- **種付きの乱数を使えば、見つかった不具合は同じ手順で再現できる**
