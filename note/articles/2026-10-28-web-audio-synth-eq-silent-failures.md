Web Audio APIでシンセサイザーとグラフィックEQを作っていて、
一番つまずいたのは「音が鳴らない」状態そのものではありませんでした。
**鳴らなくなった理由が、コンソールのどこにも出ないこと**でした。

ノードを繋ぎ忘れても、エンベロープの時刻指定を間違えても、
Web Audio APIは例外を一切投げません。`AudioContext`は正常、
ノードの生成も成功、`start()`も成功を返します。それでも音は出ません。

## この記事で分かること

- 「例外0件」がWeb Audioでは動作確認にならない理由
- ヘッドレス環境特有の無音（自動再生ポリシー）と、実装のバグによる無音の切り分け方
- パラメータを変えた直後に値を読んでも、まだ反映されていない落とし穴
- グラフィックEQの応答曲線を、どの周波数で測れば正しい値が取れるか

## 先に結論

- **「例外が出ない」と「音が鳴っている」は別の話。** 検査は`AudioContext`の状態ではなく、
  アナライザが実際に捉えた信号のピーク値まで見て初めて意味を持つ
- **`setTargetAtTime`で変えた値は、直後に読んでもまだ目標値に届いていない。**
  時定数の10倍待つ（このページでは0.02秒×10＝250ミリ秒）必要がある
- **リバーブの余韻が残っている間に「無音」判定をすると、必ず偽の不合格になる。**
  インパルス応答の長さより長く待つ
- **EQの応答曲線は、どの周波数で読むかで結果が変わる。** バンドの中心周波数ではなく、
  シェルビングフィルタが平坦になる両端で読むと設定値どおりの値が取れる

ここから先は、これらの罠がコードのどこに現れるかを、実際の実装で見ていきます。

## 自動再生ポリシーが、検査環境だけを無音にする

ヘッドレスのChromiumでページを開くと、ブラウザの自動再生ポリシーにより
`AudioContext`が`suspended`状態のままになることがあります。
この状態では、ノードの配線やパラメータの設定がすべて正しくても、
**何も鳴りません。** ここで原因を実装側のロジックに求めると、的外れな調査になります。

対策は検査起動時のフラグです。

```js
args: ['--autoplay-policy=no-user-gesture-required', '--use-fake-device-for-media-stream']
```

これを入れずに検査を書くと、「全項目が無音で不合格」という結果になり、
**実装のどこにも問題が無いのに、全滅した検査だけが残ります。**

## パラメータは、設定した瞬間にはまだ届いていない

フェーダーの値をフィルタのゲインへ渡すとき、このページでは`setTargetAtTime`で
滑らかに値を遷移させています。ここで、設定した直後に`.value`を読むと、
**まだ目標値に到達していません。**

```js
// gain は setTargetAtTime で滑らかに寄せるため、直後に .value を読むとまだ 0。
// 時定数 0.02s に対し 250ms＝10τ 待てば 99.99% 到達する
await page.waitForTimeout(250);
const fg = await page.evaluate(() => window.SYNTHEQ_DEBUG.filterGains());
```

この待ちを入れずに値を突き合わせると、「フェーダーがフィルタへ届いていない」という
**偽の不合格**が出ます。実装は正しいのに、検査の読み取りタイミングが早すぎるだけです。

## リバーブの余韻は、インパルス応答の長さより長く待つ

発音を止めても、リバーブの効果音はしばらく鳴り続けます。このページのリバーブは
インパルス応答が2.4秒あるため、無音判定の前にそれより長く待つ必要があります。

```js
// リバーブのインパルス応答が 2.4 秒あるので、余韻が切れるまで待つ（600ms では鳴り続けている）
await page.waitForTimeout(3800);
const silence = await page.evaluate(() => window.SYNTHEQ_DEBUG.peak());
check('全音停止で無音に戻る', silence < 30, `peak=${silence}`);
```

600ms程度の待ちで無音判定をすると、リバーブの余韻をアナライザが拾ってしまい、
**「音が止まらない」という誤った結論**になります。待ち時間は、効果の種類ごとに
その効果が実際にどれくらい続くかを知っていないと決められません。

## EQの応答曲線は、測る周波数を間違えると嘘の値が出る

10バンドのグラフィックEQの効果を検査するとき、カーブは対数軸で持っています。
ここで気をつけるべきは、**バンドの中心周波数の真上では、設定値どおりの値が出ない**
ということです。シェルビングフィルタは両端（低域側・高域側）で平坦になる形をしており、
その平坦部で読んで初めて設定した値どおりになります。

```js
// カーブは対数軸。両端（20Hz / 20kHz）はシェルビングの平坦部なので設定値どおりに出る
const curve = await page.evaluate(() => window.SYNTHEQ_DEBUG.curve(600));
const lowDb = curve[0];
const highDb = curve[curve.length - 1];
check('低域ブーストがカーブに現れる', lowDb > 8, `${lowDb.toFixed(1)} dB @20Hz`);
check('高域カットがカーブに現れる', highDb < -8, `${highDb.toFixed(1)} dB @20kHz`);
```

カーブの実測自体は、Web Audio APIが標準で持つ`getFrequencyResponse`を使っています。
自分で周波数応答の数式を組み立てる必要はなく、実際のフィルタノードに聞けば済みます。
この関数は、渡した周波数配列に対応する振幅と位相を`BiquadFilterNode`から直接返してくれるので、
「このフィルタは今どんな形の応答をしているか」を近似や推測なしに取得できます。

## 同時に鳴らせる声部には上限があり、止めたら必ずゼロに戻る

このシンセは同時発音数に上限（16声部）を持っています。24音同時に発音を要求しても
鳴るのは上限までで、かつ「止めたあとに声部が残っていないか」も別に確認しています。

```js
for (let i=0;i<24;i++){ D.noteOn(48 + (i % 24), 0.8); }
await new Promise(r => setTimeout(r, 300));
const during = D.voiceCount();
D.allNotesOff();
// ...
check('同時発音数に上限がある', leak.during <= 16, `during=${leak.during}`);
check('停止後に声部が残らない', leak.after === 0, `after=${leak.after}`);
```

「鳴ったか」だけでなく「止めたらちゃんと0に戻るか」を見ているのは、
鳴らしっぱなしの声部がノードを握り続けると、確認できない形でCPUと音を食い続けるためです。

## 「実際に音が出ているか」を見るための橋渡し

これらの検査が可能なのは、ページ側に検査専用の橋渡しオブジェクトを用意しているからです。

```js
if (window.__SYNTHEQ_TEST){
  window.SYNTHEQ_DEBUG = {
    // ...
    peak: () => {
      if (!AC || !analyser) return -1;
      const d = new Uint8Array(analyser.frequencyBinCount);
      analyser.getByteFrequencyData(d);
      let m = 0; for (let i=0;i<d.length;i++) if (d[i] > m) m = d[i];
      return m;
    }
  };
}
```

`peak()`はアナライザが捉えた周波数成分の最大値を返します。これが0のままなら、
ノードの接続状況やパラメータの値がどれだけ正しそうに見えても、**実際には無音**です。
この値を見ない検査は「配線は正しい」としか言えず、「音が鳴っている」とは言えません。

もう1つ、このページでは状態変数の宣言順にも注意が必要です。関数宣言は巻き上がりますが
`let`/`const`は巻き上がらないため、UI配線から呼ばれる保存処理が後方で宣言した変数を
参照すると、TDZ（一時的デッドゾーン）で起動時に丸ごと落ちます。
コード側には「`let`のまま後方セクションに置くと落ちる」という注意書きがそのまま残っています。

```js
/* 設定の保存先。saveState() は UI 配線（§10）から呼ばれるので、
   宣言は §11 ではなくここに置く（let のまま §11 に置くと TDZ で落ちる） */
const LS_KEY = 'synth-eq-v1';
let saveTimer = null;
```

この種の落ち方は、起動した瞬間に画面が真っ白のまま固まるという分かりやすい壊れ方をします。
ただ、原因が「変数の宣言位置」だと知らないと、Web Audio側の初期化処理を疑って
時間を使うことになります。コンソールには`ReferenceError`が出るので、
無音バグ群の中では例外的に気づきやすい方ですが、気づきやすいことと
原因の見当がつくことは別です。

## バイパス時にカーブが本当に平坦になっているかも検査している

EQを素通し（バイパス）にしたときは、応答曲線が設定値に関わらず常に平坦（0dB）に
戻る必要があります。これも実測で確認しています。

```js
await page.evaluate(() => window.SYNTHEQ_DEBUG.setBypass(true));
await page.waitForTimeout(120);
const flatCurve = await page.evaluate(() => window.SYNTHEQ_DEBUG.curve(600));
const flatMax = Math.max(...flatCurve.map(Math.abs));
check('バイパスでカーブが平坦になる', flatMax < 0.01, `max|dB|=${flatMax.toFixed(3)}`);
```

バイパスの実装を間違えると、「音としては素通しに聞こえるが、画面のカーブ表示だけが
以前の設定値を描き続ける」という、耳では気づきにくい形の不整合が起きます。
音を聞いて確認する項目と、画面の表示を確認する項目は別に検査しないと、
片方だけが壊れたまま残ります。

## まとめ

- **Web Audio APIは「例外が出ない」ことと「音が鳴っている」ことが無関係。**
  検査はアナライザの実測値まで見て、初めて動作確認になる
- **ヘッドレス環境の無音（自動再生ポリシー）と、実装バグによる無音は別物。**
  起動フラグで切り分けてから実装を疑う
- **滑らかに変化するパラメータは、設定した直後ではなく時定数の10倍待って読む**
- **効果音の余韻は、その効果が実際に持続する時間より長く待ってから無音判定する**
- **周波数応答は、測る場所（平坦部か遷移部か）を間違えると正しい値が取れない**
- **「鳴ったか」だけでなく「止めたら0に戻るか」まで見る。** 残った声部は気づかれないまま
  リソースを食い続ける
