Webカメラに指をかざすだけで、ページのボタンを押したりスクロールしたりできる機能を
素のJavaScriptで作りました。サーバ無し、専用アプリ無し、ブラウザだけで動きます。

**一番の壁は「ジェスチャー認識を作ること」ではありませんでした。**
カメラもGPUも無いCI環境で、この機能をどうやって機械検査するか、という点でした。

## この記事で分かること

- カメラが無いヘッドレス環境で、ジェスチャー操作を84項目も機械検査できている理由
- 合成したポインター操作が、既存のUIに届かない無言の落とし穴
- 「ちゃんと押せているか」の検査が、検査の並び順を間違えるとすり抜けること
- 指のつまみ方の個人差を、机上の純粋関数だけで安全に調整する作り方

## 3層に分けないと、1行も検査できない

この機能は3つの層に分かれています。

1. **推定層** — カメラ映像から手の関節21点の座標を取る（MediaPipe HandLandmarker）
2. **判定層**（`GestureEngine`）— 関節座標からポインター座標と押下状態を決める。**純粋なロジック**
3. **作用層**（`PointerDriver`）— 押下状態を実際のDOMイベントへ変換する

ヘッドレスの検査環境にはカメラもGPUもありません。もし3層が混ざった1つの関数だったら、
検査できるのは「ページが開くか」くらいで終わります。
推定層だけを合成データに差し替えられるようにしてあるので、判定層と作用層は
実機無しで通しで検査できます（検査は `window.__AIRTOUCH_SOURCE_FACTORY` で推定層を差し替えます）。
検査スクリプトは現在84項目です。

## 合成ポインターは、既存のUIに届かないことがある

指のつまみを「クリック」として届けるには、ブラウザへ `PointerEvent` を合成して流します。
ここで最初に踏む罠が、**合成した `pointerdown` からは互換の `mousedown` が自動生成されない**ことです。

本物のマウスやタッチなら、ブラウザが自動でPointer系とMouse系の両方のイベントを出します。
合成イベントではそれが起きません。**mouse系しか聞いていない既存のUIは、一切反応しません。**
例外は出ず、ただ無反応になります。対策は、pointer系とmouse系を両方自分で発火することです。

同じ理由で、CSSの `:hover` も合成イベントでは点きません。これはブラウザが持つ状態なので、
見た目のホバー表現は自前のクラス（`.airtouch-hover`）で付ける必要があります。

もう1つ、**オーバーレイ要素に `pointer-events: none` を付け忘れると詰みます。**
カーソル表示用の透明な層が `elementFromPoint` の対象に混ざり、
**自分のカーソル自身を拾い続けて永遠に何も押せなくなります。** 例外は出ません。

## ピンチの閾値は、往復のさせ方を間違えると検査がすり抜ける

つまみ動作（ピンチ）の判定には、押す側と離す側で2つの閾値を使います（ヒステリシス）。
1つの閾値だけだと、境目のわずかな揺れで押下が連打されてしまうためです。

この検査は単純な一発勝負では書けません。実際の検査は、ピンチ量を
`0.9 → 0.30 → 0.50 → 0.35 → 0.50 → 0.35 → 0.9` のように、**2つの閾値の“間”で何度も往復させて**から、
押下イベントが `down, up` の2回だけで終わるかを確認します。

ここには実際に踏んだ落とし穴があります。往復のさせ方を**閾値の“外”**にしてしまうと、
閾値を1つに潰す改変をしても検査の結果が変わらず、**検査が壊れていることに気づけません。**
「閾値の間で往復させる」という並びそのものが、検査の正しさを左右します。

## 個人差のある「つまみ方」は、実測の中央値から線を引く

既定のピンチ閾値は手の大きさで正規化していても、人によって合わないことがあります。
そこで「手を開く」→「指をつまむ」をそれぞれ2.5秒実測し、2つの山の間に線を引く
調整機能（`PinchCalibration` / `deriveThresholds`）を持たせました。

```js
// 2つの山の間に線を引く。押す側は近め（押しやすく）、離す側は遠め（離しやすく）
const pinchDown = closed + gap * 0.35;
const pinchUp = closed + gap * 0.65;
```

ここで大事なのは、**山が重なっていたら閾値を作らずに理由を返す**ことです。

```js
if (closed >= open) return { ok: false, reason: 'つまんだ手と開いた手の区別がつきませんでした' };
if (gap < 0.12) return { ok: false, reason: 'つまむ動きが小さすぎました（…）' };
```

無理に線を引くと「調整したのに前より当たらない」という、調整前より悪い結果になります。
判定ロジックは実機の値が無くても机上の純粋関数として全部試せる形にしてあるので、
この失敗条件（山が重なる・標本が少なすぎる）も実機無しで検査できます。

**もう1つ、調整中の押下を実DOMへ通さないことも検査しています。**
調整のたびに画面のボタンが勝手に押されたら、調整機能そのものが使い物になりません。
ここも検査の書き方に罠があって、**クリックの発生回数だけを数える検査では見抜けません。**
調整中は指をつままずに動かし続けるだけなので、そもそもクリックは発生しないからです。
実際の検査は、クリックではなく**押し始め（pointerdown）が発生していないこと**を確認します。

## 手を見失ったら、押しっぱなしを必ず解除する

手がカメラの視界から外れた瞬間に押下状態を解除しないと、**掴んだものが画面に張り付いたまま
固まります。** 判定層は手を見失った時点のフレームで、押下中なら解除イベントを出す形にしています。

## 中指つまみ＝右クリックは、人差し指の状態も見る

右クリック相当の操作は中指つまみに割り当てていますが、
親指と中指をつまむと、人差し指も自然に親指へ寄ってきます。
**中指だけを見ていると、普通のタップのたびに右クリックメニューが出てしまいます。**
そのため「人差し指が開いている」ことも条件に加えています。

## ライブラリの版は2か所にあり、ずれると別の版を読み直す

手の認識モデルを読み込むライブラリの版は、`gesture-pointer.js` 内の `VISION_VERSION` と、
importmapの両方に書かれています。この2つがずれると、**SRI（integrity）検証を通った版とは
別の版を、importmapの外から直接URLで読み直してしまいます。** 例外は出ず、
「なぜか動きが変わった」だけが残ります。検査はこの2つの値を文字列として突き合わせます。

## まとめ

- **実機が無いと検査できない機能は、推定・判定・作用の3層に分けて判定層だけを独立させる**
- **合成イベントは、本物のポインターが自動でやってくれることを自動でやってくれない。**
  Mouse系の自動生成・`:hover`・`pointer-events` は個別に手当てが要る
- **ヒステリシスの検査は、往復のさせ方自体が検査の正しさを決める。**
  閾値の外で往復させると、閾値を壊す改変が素通りする
- **個人差のある調整は、失敗条件（山の重なり）を握りつぶさない。** 無理に線を引くより
  「調整できなかった」と伝える方が、使う人にとって安全
- **バージョン番号を2箇所に持つなら、一致を検査で縛る。** ずれても例外は出ない
