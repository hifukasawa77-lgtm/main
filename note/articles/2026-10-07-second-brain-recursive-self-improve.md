AIエージェントに「学んだことをメモしておいて」と指示するだけでは、
**次のセッションはほとんど何も学びません。**

私はこれをリポジトリ内にMarkdownの「セカンドブレイン」（`obsidian-vault/`）を作った直後に
思い知りました。学びは確かに蓄積されていく。でも肝心の`04-Knowledge/`（再利用可能な知見を
置く場所）は、セッション開始時に読み込まれる仕組みが**一切ありませんでした。**
最も価値の高い教訓が、毎回まるごと素通りされていたということです。

この記事は、その反省から組んだ「蓄積→想起→反映」の閉じたループと、
**そのループを作る過程で踏んだ、ループ自身の無言バグ**の記録です。

## この記事で分かること

- なぜ「Markdownに書く」だけでは自己改善にならないのか
- セッション開始時の自動読み込み（想起）が、環境依存のバグで**土台から壊れていた**実例
- 学びを恒久ルールへ「昇格」させる仕組みと、それをあえて機械では強制しない理由
- 検査を書く側にも、検査対象と同じ「無言で壊れる」バグが刺さった実例

## 先に結論

- **蓄積だけでは閉じない。** 「想起（毎回自動で読み込む）」「反映（恒久指示への昇格）」
  「機械検査（劣化の自動検出）」の3つが揃って初めてループになる
- **想起の層そのものが、環境依存のバグで壊れうる。** 「動いているように見える」ことと
  「正しく機能している」ことは別で、これを確かめる検査が要る
- **判断が必要な工程（昇格すべきか）は、機械で強制しない。** 非ブロッキングの警告に留め、
  最終判断は都度人とAIに残す設計にした
- **検査を書く側の言語（シェル）にも、対象と同種の無言バグが潜む。** ロケール依存で
  検査自体が空振りし、「緑になった」が「正しく検査された」を意味しない状態が起きた

ここから先は、上の4点それぞれがどう実際に起きたかを、コードと日付付きで見ていきます。
どれも「例外は出ない」「エラーメッセージも無い」まま、想起や検査という
**信頼して動かしているはずの土台側**が静かに間違った結果を返していた実例です。
自分でセカンドブレインや自己改善ループを組んでいる人には、
そのまま同じ形で刺さる可能性が高いと思っています。

## 1. 04-Knowledge/ が一度も読まれていなかった

**何が起きたか。** セカンドブレイン（`obsidian-vault/`）を作った当初、
SessionStart hookが読み込んでいたのは `MOC.md`（目次）と直近のDaily Noteだけでした。
知見を溜める場所である `04-Knowledge/` は、**書く場所はあるのに読む導線が無かった。**

**なぜ問題だったか。** 蓄積はできているので「学びは記録されている」ように見えます。
ただ、次のセッションが自発的に `04-Knowledge/` を開かない限り、その知見は一度も使われません。
**「書いた」と「効く」の間に断絶がある**状態です。

**どう直したか。** `second-brain-recall.sh` に、`04-Knowledge/` の各ノートから
H1見出しだけを抜き出す「知見クイックインデックス」を追加しました。

```bash
# 04-Knowledge/ の再利用可能な知見を「クイックインデックス」として常時投入する。
# 全文は重いので各ノートのH1見出しのみを列挙し、必要な知見へ最短で辿れるようにする。
if compgen -G "$VAULT/04-Knowledge/*.md" > /dev/null; then
  echo "### 知見クイックインデックス（04-Knowledge/ — 詳細は各ファイル参照）"
  for f in "$VAULT"/04-Knowledge/*.md; do
    title=$(grep -m1 '^# ' "$f" 2>/dev/null | sed 's/^# //' || true)
    base=$(basename "$f" .md)
    echo "- [[$base]] — ${title:-$base}"
  done
fi
```

全文を毎回投入すると次第にコンテキストを食い尽くすので、見出しだけを一覧にして、
「必要ならここを見に行ける」導線だけを常に確保する形にしています。
これと対になるのが `/self-improve` スキルです。学びを読むだけで終わらせず、
**エージェント定義・CLAUDE.md・スキル・フックという「指示そのもの」に昇格させる**
工程を独立させました。想起だけでは学びは毎回読み直されるコストのまま残り、
指示に昇格して初めて自動で効くようになるからです。

## 2. 想起の土台そのものが mtime バグで壊れていた

**何が起きたか。** 「直近のDaily Note」を選ぶのに、当初は `ls -t`（更新時刻順）を
使っていました。これは通常の開発環境では問題なく動きます。ところが、
このプロジェクトはリモート実行環境でセッションごとに**リポジトリをフレッシュクローン**します。
フレッシュクローンでは、リポジトリ内の全ファイルの mtime が**ほぼ同時刻**になります。

**何が起きたか（実害）。** ある日、`ls -t` が本当の最新Daily（当時の07-05）ではなく
`06-28` を「最新」として選び、そのまま想起されました。
**閉ループの入口である「想起」が、静かに古い情報を投入していた**ということです。
コンソールにエラーは出ません。hookは正常終了します。ただ、投入される内容が違うだけです。

**どう直したか。** ファイル名の日付（`YYYY-MM-DD.md`）で比較する方式に変更しました。

```bash
# mtime順(ls -t)は使わない: CCRリモート環境はフレッシュクローンで全ファイルのmtimeが
# ほぼ同一になり最新判定が壊れる。ファイル名が YYYY-MM-DD.md なので名前順が正。
LATEST_DAILY=$(ls "$VAULT/01-Daily"/*.md 2>/dev/null | sort | tail -1 || true)
```

さらに、同じ種類のバグが他のスクリプトに潜んでいないかを機械で確認する検査を追加しました。
`ls -t` や `find -newer` のようなmtime依存パターンを `.claude/hooks` と `.claude/skills`
から探し、検査スクリプト自身は自己除外し、コメント行も除外します。

```bash
MT=$(grep -rnE 'ls[[:space:]]+-[a-zA-Z]*t|find[[:space:]].*-newer|sort[[:space:]].*-k.*%Y' \
  .claude/hooks .claude/skills --include='*.sh' --include='*.cjs' 2>/dev/null \
  | grep -v 'harness-lint.sh' \
  | grep -vE '^[^:]+:[0-9]+:[[:space:]]*#' || true)
```

**この事例が示すのは、「ループの土台自体が壊れうる」ということです。**
学びを溜める仕組みを作っても、その仕組みを動かす基盤（この場合はファイル選択ロジック）が
環境依存で壊れていれば、ループ全体が気づかれないまま劣化します。

## 3. 昇格し忘れた学びを、手作業の grep で見つけた

**何が起きたか。** ある時点で、複数のDaily Noteに書かれた「学び」セクションが、
実際には恒久ルールへ昇格されずに残っていることが手作業の点検で見つかりました。
`grep -L 昇格済み` でDaily Note群を洗ったところ、直近2日分だけでなく、
**さらに以前の2日分でも昇格漏れが見つかりました。**

**なぜ起きたか。** 学びは書いた直後は「まだ昇格していない」状態が正常です。
`/self-improve` を実行し忘れたまま次のタスクに進むと、その学びは「読めば分かる」状態のまま
放置され、毎セッションのコンテキストコストになるだけで指示には反映されません。

**どう直したか。** 昇格マーカーの規約を作り、検査で漏れを機械的に列挙するようにしました。

- 学びが恒久ルールに昇格されたら `昇格済み（YYYY-MM-DD）`
- 別経路で反映済みと確認できたら `反映済み`
- 一回限りで昇格対象外と判断したら `昇格しない`

このマーカーが無い「学び」セクションを含むDailyを検査で警告します。

**あえて警告（△）に留めた理由。** 「この学びを昇格すべきか」の判断はLLMと人の作業で、
機械には判定できません。ここを不合格（✗）にすると、**新しいDaily Noteを書くたびに
検査が赤くなる**という誤設計になります。判断が要る工程は、機械で"できたつもり"にしない、
というのがここでの割り切りです。

## 4. Daily Noteごと書かれなかった日は、上の検査でも見えない

**何が起きたか。** 3の検査は「存在するDaily Noteの昇格漏れ」しか見えません。
ある日には**大きめの実装を5件行ったのに、Daily Noteそのものが1本も作られませんでした。**
その日の学びは、蓄積ループの入口にすら乗っていません。

**どう直したか。** 直近14日分のコミット履歴と、対応する日付のDaily Noteの有無を
突き合わせる検査を追加しました。コミットはあるのにDailyが無い日を警告します。
古い作業日を延々と警告し続けないよう、期間を14日に絞っています。
これも判断（記録すべきだったか）は人の作業なので、非ブロッキングの警告のままです。

## 5. 検査を書く側の言語にも、同じ「無言で壊れる」病が住んでいた

ここが一番おもしろいところです。**「無言で壊れるバグを機械検査で防ぐ」という活動自体の中で、
その検査がまったく同じ種類の無言バグを踏みました。**

**何が起きたか（1件目）。** Routineのスケジュール表記のズレを検出する検査を最初に実装したとき、
`[月火水木金土日]` のような日本語のブラケット表現を使いました。
シェルの `LANG` が未設定（Cロケール）の実行環境では、この多バイト文字のブラケット表現は
**バイト単位比較になり、必ず空振りします。** そしてこれが厄介なのは、
**エラーにならず、検査が「通った」ように見える**ことです。緑が偽物だったということです。

**どう直したか。** 多バイト文字はブラケットに入れずリテラルで置き、可変部分は
単バイトの否定クラスで書くようにしました（`毎週[^ ]*曜` のような形）。
再発防止として、`.claude` 配下の `.sh` ファイルから多バイトブラケット表現を検出する
検査そのものを追加しました。

```python
pat = re.compile(r'\[\^?[^\]\n]*[^\x00-\x7F][^\]\n]*\]')
# ...
for i, l in enumerate(lines, 1):
    if l.strip().startswith('#'):   # 解説コメントは対象外（自己誤検出の回避）
        continue
    if not re.search(r'grep|sed|awk', l):
        continue
    m = pat.search(l)
    if m:
        out.append('%s:%d: [多バイトブラケット] %s' % (p, i, m.group(0)[:40]))
```

**何が起きたか（2件目、別の検査で）。** 日英併記のチェックを行うi18n検査で、
`grep -P` の `\x{...}`（Unicodeコードポイント指定）を使った箇所がありました。
Cロケールでは、PCRE がコードポイントを大きすぎると判断してエラー終了し、
**grepは常に「該当なし」を返します。** 結果、日本語を含む全ページが
「日本語表記が含まれていない」という誤判定を受けました。修正は `(*UTF)` を付けて
PCREにUTF-8として解釈させることです。

**この2件から言えること。** ロケール依存の文字コード処理は、シェルスクリプトでは
**エラーを出さずに黙って空振りする**という性質を持っています。ゲームのCanvas描画で
「範囲外の`drawImage`は例外を出さず何も描かない」のと、構造的にまったく同じ形です。
無言で壊れるバグは対象がゲームか検査スクリプトかを問わず、同じ原因（境界外・環境差分の
扱いを例外にしていない）から生まれます。

## まとめ

- **「Markdownに書く」と「AIが学ぶ」の間には、想起・反映という別工程が要る。**
  蓄積だけでは学びは毎回読み直されるコストのまま残り、指示に昇格して初めて自動で効く
- **想起の仕組み自体が環境依存で壊れることがある。** 「実行できている」ことと
  「正しいものを読み込んでいる」ことは別で、これを見分ける検査が必要
- **判断が要る工程は機械で強制しない。** 昇格すべきかの判断は人とAIに残し、
  検査は「見落としを列挙する」役に留める。これを取り違えると、正常な作業のたびに
  検査が赤くなる誤設計になる
- **検査を書く言語自体にも無言バグが住む。** シェルスクリプトのロケール依存の
  文字コード処理は、エラーを出さずに空振りする。検査だから安全ということはない
