AIエージェントに「ツールを好きに使っていい」権限を渡すと、
**課金が発生するツールまで同じ扱いで実行してしまう。**

個人開発のリポジトリでAIエージェントに作業を任せる以上、
この問題は一度は向き合うことになります。私はこれを、
AIが呼ぼうとしたツールを**実行される前に**横取りして、
金額次第で止めるか確認を求めるhook（`accounting-guard.sh`）で解決しました。

## この記事で分かること

- 課金ガードを「外側ゲート」と「内側判定」の2段に分ける理由
- 2段のうち片方だけを直すと、**フック自体が発火せず無言で素通りする**実例
- 予算ファイルをJSONにせず、Markdownのままシェルで読める形にした設計
- 例外（上限の中にもう一つ上限を作る枠）を安全に運用する方法

## 先に結論

- **課金リスクのあるツール名は、2つの場所で別々に判定している。**
  「そもそもフックを起動するか」（settings.jsonの`matcher`）と
  「起動したフックの中で止めるか」（hook内の判定リスト）は別物で、
  **前者が後者を包含していないと、フックの中身を直しても何も変わらない**
- **判定リストは3箇所に存在する**（監視対象の一覧・hookの判定式・settings.jsonのmatcher）。
  1箇所だけ更新すると、残りとズレて検知漏れの隙間ができる
- **予算ファイルはMarkdownのままで機械可読にできる。** `KEY: VALUE`の行をgrepで
  抜くだけで、jq等の追加ツールなしにシェルスクリプトから数値を取れる
- **全か無かの上限の中に、専用の小さな上限を作ることもできる。** ただし二重の
  安全装置（提供元側のハード上限＋呼び出し側の事前チェック）を両方持たせないと、
  「気をつける」に逆戻りする

ここから先は、実際にこの仕組みがどう組まれているか、コードそのものを見ていきます。
AIエージェントに何らかの実行権限を渡している人であれば、
「止めるつもりだったのに止まらない」という形の落とし穴は、
課金に限らずどこかで同じ構造に当たるはずです。

## 1. 課金ガードは2段構えで、片方だけ直すと発火しなくなる

ガードの仕組みは、Claude Codeの`PreToolUse` hookとして実装されています。
ツールが実行される**前**にこのスクリプトへペイロードが渡り、
`allow`/`ask`/`deny`のいずれかを返すことで実行を制御します。

ここで2段構えになっているのが要点です。

**外側ゲート**（`.claude/settings.json`の`matcher`）は、「このツール名のときだけ
hookを起動する」というClaude Code側の仕組みです。

```json
"matcher": "asset_license_and_download_stock|license_and_download|purchase|checkout|subscribe|billing|payment"
```

**内側判定**（`accounting-guard.sh`の`BILLING_RISK_TOOLS`）は、hookが実際に起動した
あとで「このツール名なら止める」を判定する正規表現です。

```bash
BILLING_RISK_TOOLS='asset_license_and_download_stock|license_and_download|purchase|checkout|subscribe|billing|payment'
echo "$TOOL_NAME" | grep -Eq "$BILLING_RISK_TOOLS" || exit 0  # リスク該当なし→素通り
```

**この2つがズレると、内側判定だけを直してもガードは効きません。**
外側ゲートがそもそもhookを起動しなければ、内側の判定式は一度も評価されないからです。

実際にこの2つに不一致が見つかったことがあります。settings.json側は
`license_and_download_stock`（`asset_`接頭辞なし）を要求していたのに対し、
guard.sh側は`asset_license_and_download_stock|license_and_download`
（接頭辞ありと無し両方）を判定対象にしていました。当時使っていた実在のツール名は
両方の表現にマッチしていたため実害は出ていませんが、**guard.shが拾うはずの
`_stock`無しのツール名が将来来たら、外側ゲートで弾かれてhook自体が起動せず、
ガードが無言で素通りする**という潜在的な隙間になっていました。

対応は「外側ゲートの文字列を内側判定と完全に同一にする」ことです。
**外側ゲートは内側判定の上位集合（同一文字列）でなければならない**、
という不変条件を両方のファイルのコメントに明記して再発を防いでいます。

## 2. 同期しておく場所は、実は3箇所ある

課金リスクのあるツール名の一覧は、上の2箇所に加えて、
経理エージェント（`.claude/agents/accounting-agent.md`）が持つ監視対象のテーブルにも
存在します。つまり同期対象は**3箇所**です。

- 経理エージェント定義の監視対象テーブル
- `accounting-guard.sh`の`BILLING_RISK_TOOLS`
- `settings.json`のPreToolUse `matcher`

新しい課金リスクツールを追加するたびに、この3箇所を同時に更新する必要があります。
1箇所でも更新を忘れると、「エージェントの定義には書いてあるのに、実際には止まらない」
という状態が生まれます。ここは機械で強制しているわけではなく、
各ファイルのコメントで明示して人の作業として維持している部分です。

## 3. 予算ファイルは、JSONではなくMarkdownのまま機械可読にする

予算の定義（`accounting/budget.md`）と当月の累計（`accounting/ledger.md`）は、
どちらも人間が読むMarkdownのドキュメントです。ただし中に
`KEY: VALUE`形式の行を埋め込むことで、シェルスクリプトからも直接読めるようにしています。

```markdown
MONTHLY_LIMIT: 5000
```

```bash
MONTHLY_LIMIT="$(grep -oE 'MONTHLY_LIMIT:[[:space:]]*[0-9]+' "$BUDGET_FILE" | grep -oE '[0-9]+' | head -1 || echo 5000)"
CURRENT_TOTAL="$(grep -oE 'CURRENT_TOTAL:[[:space:]]*[0-9]+' "$LEDGER_FILE" | grep -oE '[0-9]+' | head -1 || echo 0)"
```

guard.sh内のコメントにある通り、これは「jqが無くても動くように」という設計です。
hookを動かす実行環境にJSONパーサが入っているとは限らないので、
`tool_name`の抽出も同じくgrepとsedだけで行っています。

```bash
TOOL_NAME="$(printf '%s' "$PAYLOAD" \
  | grep -o '"tool_name"[[:space:]]*:[[:space:]]*"[^"]*"' \
  | head -1 | sed 's/.*"tool_name"[[:space:]]*:[[:space:]]*"//; s/"$//' || true)"
```

**予算ファイルも台帳ファイルも存在しなければ、hookは何もせず素通りします**
（`[ -f "$BUDGET_FILE" ] || exit 0`）。依存ファイルが欠けている状態を
「エラーで止める」ではなく「ガード無しで通す」扱いにしているのは、
このhookがほかの全ツール呼び出しの前段に挟まる以上、設定ミスでAI作業全体を
止めてしまうことの方が避けたい失敗だという判断です。

## 4. 二値のゲートと、人間向けの段階的なしきい値は役割が違う

hook自体が返せる判定は`ask`（深澤の確認を求める）と`deny`（拒否する）の二値です。

```bash
if [ "$CURRENT_TOTAL" -ge "$MONTHLY_LIMIT" ]; then
  # deny: 上限到達済みなら停止
else
  # ask: それ以外は確認を要求
fi
```

一方で`budget.md`には`ALERT_THRESHOLD_NOTICE`（70%）・`ALERT_THRESHOLD_WARN`（90%）・
`ALERT_THRESHOLD_STOP`（100%）という3段階のしきい値が定義されています。
hookのコード自体は100%到達の判定しか見ていません。70%・90%の通知は、
経理エージェントがリスクをRED/YELLOW/GREENの3段階で報告する役割の側に属します。

つまり**「実行を機械的に止めるか」と「状況を人間に分かりやすく伝えるか」は、
別のレイヤーで扱っている**ということです。hookに全部の判断を詰め込むと、
文言の調整のたびにシェルスクリプトを触ることになり、却って事故のリスクが増えます。

## 5. 上限の中にもう一つの上限を作る（ZERO-1のクラウドLLM枠）

このプロジェクトの大前提は課金ゼロの維持ですが、唯一の例外として、
別リポジトリのZERO-1（ローカルLLMのPC版）のクラウドLLM呼び出しに限り、
月¥3,000までの枠が認められています。これは全体の上限¥5,000の**内数**であり、
別枠で追加されるものではありません。

ここで例外を安全に運用するための条件が2つ明記されています。

- **上限は二重に守る**: ①提供元の管理画面でハード上限を人が設定する
  ②呼び出し側のアプリ自身が、呼ぶ前に当月消費を見て止める。
  「気をつける」という運用だけでは上限が上限として機能しないという判断です
- **単価が分からないモデルは呼ばない**: 価格表に無いモデルは、
  いくらかかるか分からないので止めます。推測で見積もると、
  その推測が外れた時点で上限が上限でなくなります

例外を作るときに大事なのは、「全体の上限を緩める」のではなく
「全体の上限の中に、独立した小さな上限を作り、その小さな上限自体にも
二重の安全装置を持たせる」という形にしていることです。例外が1つ増えるたびに
守りが薄くなる作り方は採っていません。

## まとめ

- **「ゲートを起動するか」と「ゲートの中で判定するか」は別の層で、
  両方が同じ判定基準を持っていないと片方の修正が無意味になる**
- **判定基準が複数ファイルに分散しているなら、同期対象をコメントで明示する。**
  機械で強制できない同期は、気づける形にしておくしかない
- **機械可読性は、JSON化しなくても手に入る。** `KEY: VALUE`形式の行を
  Markdownに埋め込み、grepで読むだけで十分な場合がある
- **二値の実行ゲートと、段階的な人間向け警告は分けて設計する。**
  1つのコードに両方を詰め込むと、文言調整のたびに実行ロジックを触ることになる
- **例外を作るときは、全体の緩和ではなく独立した小さな枠を作り、
  その枠自体にも二重の安全装置を持たせる**
