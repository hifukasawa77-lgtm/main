# 2026-09-03

## 今日やったこと
- ZERO-1 Mobile が実機で「エラーは出ないが 0% のまま進まない」件を直した
  （ブランチ `claude/zero-1-mobile-startup-error-9ajqwk`）
  - モデルの読み込みを **Web Worker（`assets/js/zero1-worker.js`）へ追い出した**
  - 進捗と一緒に **経過時間を毎秒表示**（0%が固まりなのか進行中なのかを区別できるようにした）
  - 取得先の確認に **時間切れ**（`AbortSignal.timeout`）を入れた
  - **メモリが足りないモデル**に警告を出すようにした
  - 検査 57 → 68項目

## 学んだこと・気づき
- **「0%のまま進まない」の正体は、たいてい画面の糸が塞がっていること**。モデルの読み込み
  （取得・WebAssemblyのコンパイル・GPUへの転送）を画面と同じ糸でやると、その数分ぶん
  画面がまるごと固まる。**進捗バーも再描画されない**ので、進んでいるのか止まっているのかが
  誰にも分からなくなる。深澤さんのスクリーンショットは画面の一部だけが描き変わる崩れ方をしていて、
  それが「主たる糸が塞がっている」という唯一の手掛かりだった
- **「進捗%」だけでは足りない。経過時間を毎秒書き換えること**。時計が動いていれば
  「遅いだけ」、止まっていれば「固まっている」と、利用者にも作った側にも一目で分かる。
  ＝**時計が動いていること自体が、画面の糸が空いている証拠になる**
- **`fetch` には既定の制限時間が無い**。相手が接続だけ受けて何も返さない（回線側のフィルタ等）と
  **永遠に待つ**。例外も出ないので「固まった」としか見えない。前回入れた接続確認に
  時間切れを付け忘れており、**自分で新しい 0% 固まりを作りかけていた**
- **「糸が壊れた」と「モデルが失敗した」を混同しない**。worker の中でモデルが落ちたのを
  「worker が使えない端末だ」と読み違えると、同じ失敗を画面と同じ糸でもう一度やって二度手間になり、
  しかも次からずっと固まる経路へ落ちる。**この読み違えは自分で書いて、検査#40 が捕まえた**
  （＝検査を先に用意しておくと、書いた直後の間違いをその場で拾える）
- **空き容量とメモリは別の話**。これまで一覧に出していたのは空き容量だけで、メモリ4GBの端末に
  2.5GBのモデルを警告なしで選ばせていた。載らないモデルは**取得だけ最後まで進んでから**
  GPUへ載せる段で固まる——例外が出ないので、やはり「進まない」としか見えない
- **故障注入はインデントまで合っていないと無意味**。時計を止める注入が空振りしていたのに
  「検査は通った＝壊しても落ちない」と読みかけた。置換が当たったことを確かめてから
  結果を読むこと（今回は `assert old in s` を足して初めて本当に落ちた）

## 意思決定
- worker が使えない端末では**画面と同じ糸へ落として続行する**（動かないより固まる方がまし）。
  ただし落ちた事実は失敗パネルの「モデルを動かした糸」に必ず出す
- メモリ不足のモデルも**選ぶこと自体は止めない**。`navigator.deviceMemory` は 8 で頭打ちの
  粗い値で、これを根拠に禁止すると動く端末まで妨げる。警告に留める

## 次回への引き継ぎ
- 深澤さんの端末で再確認。**「日本語に強い」（2.5GB / 目安6GB）はメモリ4GBの端末には重い**ので、
  まず「ふつう」（1.9GB / 目安4GB）で通ることを見てから、日本語版を試すのがよい
- 経過時間が動いていれば進行中。止まっていれば、その時点の秒数と段階をそのまま知らせてもらう

## 追記: それでも0%のまま進まなかった（2回目の報告）

別の糸へ追い出した版でも進まなかった。ただし**画面写真の情報量が段違いに増えた**——
経過時計が「2分18秒経過（2分18秒進んでいません）」と出ており、これで
**①画面の糸は空いている（時計が動いている）②WebLLM の進捗が1度も来ていない**
の2つが同時に分かった。前回は「0%」しか無く、どちらも判別できなかった。

### 原因（作りの穴）
- **worker は「作れても動かない」**。`new Worker()` は中の読み込みが失敗しても例外を投げず、
  失敗した糸は**ただ黙る**。`CreateWebWorkerMLCEngine` は返事を待ち続けるだけなので、
  **例外もエラーも出ないまま0%で永久に止まる**
- **WebLLM の読み込みには時間切れが無い**。取得先が黙る・糸が死ぬ・メモリが尽きる、
  どの場合でも同じ「永久に0%」になる。待ち続けるのが一番いけない

### 直したこと
- worker 自身に「動き出した」と言わせる（`{zero1:'ready'}`）。合図が来なければ
  画面と同じ糸へ落とす。worker 側は `unhandledrejection` も拾って理由を送り返す
- `stallGuard()`: 進捗が出ていない時間に上限を設けた（初回90秒／以降240秒）。
  超えたら「◯秒のあいだ1つも進みませんでした」を持って失敗にし、軽いモデルを促す
- 経過時計に**いまどの段階か**を添えた。画面写真1枚で止まった場所が分かる
- 失敗の手掛かりに「別の糸が動かなかった理由」「進捗が1度でも出たか」を追加

### 学んだこと・気づき
- **待ち続ける実装は、必ず「永久に0%」になる**。時間切れの無い待ちを1つでも残すと、
  相手が黙った瞬間に**理由の無い沈黙**へ変わる。そこに至る全ての段（接続確認・糸の起動・
  モデルの準備）に上限を置いて初めて、利用者の手元に何かが残る
- **診断は1往復ごとに情報量が増えるように作る**。今回、時計と段階を出したことで
  次の画面写真からは「どこで止まったか」が読み取れる。**直せなくても、切り分けが進む形に
  作り替えるのは前進**（前回の写真は「0%」だけで何も分からなかった）
- **検査が実物を通っていないと、実機の失敗を再現できない**。合成の worker で
  済ませていた検査を、`page.route` でCDNだけ差し替えて**実物の Worker で合図を往復させる**
  形に直したら、その場で「CDNが落ちると黙る」経路が再現できた
- **実時間で待つ検査は、遅いだけで落ちる**。上限値は `window.__ZERO1_TIMEOUTS` で
  差し替えられるようにした（90秒を検査で実際に待たせない）

### 次回への引き継ぎ
- 深澤さんの端末で再確認。**今度は必ず何らかの結果が出る**（成功／失敗パネル）。
  90秒〜4分で止まりと判定され、失敗パネルに
  「別の糸が動かなかった理由」「進捗が1度でも出たか」「配信経路」が出る
- 「進捗が1度でも出たか: いいえ」なら取得の入口（huggingface.co）で詰まっている。
  「はい」なら途中で失速している。ここで初めて次の手が分かれる

## 追記: 起動したが答えられない（3回目の報告・原因は別物だった）

**起動には成功した**（かるい / Qwen2.5-0.5B-q4f32、チャット画面まで到達）。
ところが最初の問いかけで:

```
AbortError: Failed to execute 'mapAsync' on 'GPUBuffer':
A valid external Instance reference no longer exists.
```

### 原因
**読み込みのあいだに画面が消えて、AndroidがGPUの資源を手放していた。**
モデルは載り終わっているのに、切断は**最初の返事の瞬間まで表面化しない**。
利用者から見ると「起動はしたのに答えない」——一番分かりにくい壊れ方になる。

### 直したこと
- **そもそも切らせない**: 読み込み中は Screen Wake Lock で画面を消させない
  （数分かかる読み込みが引き金なので、ここが本命）。画面が戻ったら取り直す
- **切れても諦めない**: `isDeviceLost()` で判別し、**黙ってモデルを載せ直して答え直す**。
  モデルは端末に残っているため取得はやり直さず数秒で戻る。利用者に打ち直させない
- 載せ直しても戻らないときだけ、「再読み込みしてください（モデルは残っているので次はすぐ起動します）」

### 学んだこと・気づき
- **失敗は、起きた場所と現れる場所が違う**。GPUが切れたのは読み込み中なのに、
  露見したのは最初の返事。**症状の出た場所だけを見ると原因に辿り着けない**
- **「予防」と「回復」は両方いる**。Wake Lock（予防）だけでは、電話が来た・タブを移した等で
  やはり切れる。載せ直し（回復）だけでは、毎回数秒待たされる
- **回復の対象は狭く保つ**。`isDeviceLost()` を広げて通信やシェーダーの失敗まで含めると、
  直しようのない失敗まで何度も載せ直すことになる（故障注入Cで確認）
- **同じ「動かない」でも、報告のたびに原因は別物だった**——SWの横取り → 画面の糸の詰まり →
  黙る worker → GPUの切断。**1つ直すと次が見える**ので、毎回「切り分けが進む形」に
  作り替えたのが結果的に一番効いた

### 次回への引き継ぎ
- 深澤さんの端末で再確認。切れても自動で載せ直すので、体感では「少し待って答えが出る」になるはず
- 会話が通ったら、次は「ふつう」（1.8GB）で賢さを上げられるか試す

## 追記: ブラッシュアップ（起動できた後の体験へ）

「動かない」を4回直したあと、初めて**起動できた後**に手を入れた。
提案7点すべてを実装（ブランチ `claude/zero-1-brushup-uunej2`、検査 77 → 117項目）。

1. 生成の中断ボタン／2. 保存済みモデルの検知と削除口／3. 返答の体裁・コピー・読み上げ／
4. 聞き方の候補／5. 渡していない文脈の境目／6. 速さの可視化／7. ホーム画面アプリ化＋圏外

### 学んだこと・気づき
- **「動く」と「使える」の間には、例外もエラーも出ない不便がずらっと在る**。
  止められない・2回目も初回扱い・消す口が無い・記号が素のまま・覚えていないのに
  覚えているように見える。どれも壊れてはいないので、検査でも報告でも上がってこない。
  **画面を実際に触ってみるまで、一つも見えなかった**
- **失敗の設計だけを作り込んでも、成功したときの体験は良くならない**。
  これまでの4回は全部「失敗をどう伝えるか」だった。それは正しかったが、
  成功経路には一度も手が入っていなかった
- **体裁を整える＝モデルの出力を解釈するということ**。ここで innerHTML を使うと
  返答経由のXSSの道ができる。CSPを固めても同一ページ内のDOM生成は素通りするので、
  「CSPがあるから安全」は通用しない。検査#80で実際に流し込んで確かめた
- **故障注入は「その経路を通る検査があるか」まで見ないと意味がない**。境目の位置を
  わざと壊したのに検査が素通りした——検査が「あいさつ文が在る状態」を通っていなかった。
  検査#89を足して初めて捕まった。**素通りした故障注入は、検査の穴の在りかを教えてくれる**
- **誤検知の解消は、検査を弱める以外の手でやる**。a11y監査が私のコメント中の
  img タグ文字列に反応した。閾値を緩めるのではなくコメントの書き方を変えた。
  誤検知を許した検査は、やがて誰にも見られなくなる
- **const は巻き上がらない**（3度目）。橋渡しへ載せる定数を後方で宣言して起動ごと落とした。
  synth-eq の saveTimer と同じ形で、CLAUDE.mdにも書いてあったのに踏んだ

### 意思決定
- **WebLLM本体をリポジトリへ同梱するかは保留**。同梱すれば同一オリジンになり、
  既存のSW（cache-first）がそのまま拾って圏外での起動が保証できる。ただし
  CLAUDE.mdの「ライブラリはCDN経由」方針と正面からぶつかり、版上げが手作業になる。
  今回は方針を曲げず、**取れなかったときの理由を必ず出す**ところまでで止めた（深澤判断待ち）
- **メモリ・空き容量の警告は、保存済みなら出さない**。すでに端末にあるものへ
  「空きが足りません」と出して起動を止めるのは端的に誤り

### 次回への引き継ぎ
- 深澤さんの端末で確認したいのは3点: ①ホーム画面に追加して開けるか
  ②2回目の起動が「保存済み・すぐ起動します」になり、実際に数秒で立ち上がるか
  ③長い返答を「■ 止める」で止められるか
- 実測の tok/秒 が出るので、note記事の一次情報として使える

## 追記: 起動したのに答えられない（5回目の報告・また別の顔だった）

ブラッシュアップ版を実機で確認したところ、**起動には成功**（ふつう / Standard・
起動1分01秒・チャット画面まで到達）したのに、最初の質問で英文が出た:

```
答えられませんでした: Error: Unable to find a compatible GPU. ...
```

### 原因
中身は3回目と同じ「読み込み中にGPUとの接続が切れた」。ところが**文言が違った**——
切れたGPUを取り直そうとした WebLLM が `requestAdapter()` から null を受け取ったときの
メッセージで、`isDeviceLost()` の判定に入っていなかった。結果、**前回作り込んだ
「黙って載せ直す」が一度も走らず**、打つ手の無い英文だけが利用者に残った。

### 直したこと
- `isDeviceLost()` に「GPUが見つからない」系を追加。広げる足場は
  **この判定を見るのは `send()` だけ＝起動に成功した後だけ**という位置関係
- `waitForAdapter()`: 切れた直後は `requestAdapter()` が null を返し続けるので、
  戻るのを待ってから載せ直す（上限15秒・待ち続けない）
- 載せ終わった直後と、画面が戻ったときにもアダプタを確かめ、**聞かれる前に**載せ直す
- 生成中も wake lock を取る（長い返答の途中で画面が消えても切れる）
- 自分で投げる例外に英文を混ぜない（判定の目印は `name` に持たせる）

### 学んだこと・気づき
- **同じ故障が同じ文言で来ると思ってはいけない**。3回目と5回目は原因が同一なのに
  メッセージが全く違い、正規表現による判定がそのまま素通りした。**判定を文言に
  依存させる以上、文言は増えると考えて足場（どこから呼ばれるか）で安全を担保する**
- **「直した」の検証は、直した経路が実際に走ったかまで見る**。前回の載せ直しは
  検査では動いていたが、実機では**入口の判定で弾かれて一度も走っていなかった**。
  検査が通っていたのは、検査が3回目の文言しか投げていなかったから
- **故障注入が実機の画面を再現できると、直ったことの確度が上がる**。判定を元に戻す
  注入Fで「答えられませんでした: Unable to find a compatible GPU.」が完全に再現できた
- **検査の引数リストの取りこぼしは、製品の故障に化ける**。addInitScript の分割代入に
  新しい引数を足し忘れ、初期化ごと ReferenceError で落ちて「WebGPU非対応の端末」に
  なっていた。製品側を疑いかけた
- 検査が製品の実バグを1件見つけた: GPU復旧の経路で `node.textContent` を代入しており、
  吹き出しの本文要素（`.body`）ごと消えて、以後の体裁・コピー・添え書きが付かなくなっていた

### 次回への引き継ぎ
- 深澤さんの端末で再確認。今度は英文ではなく、①黙って載せ直して答えが出る、
  ②戻らなければ日本語で「ページを再読み込みしてください」が出る、のどちらかになる
- 読み込みが1分かかる間に画面を消さない／他アプリへ移らないと、そもそも起きない
