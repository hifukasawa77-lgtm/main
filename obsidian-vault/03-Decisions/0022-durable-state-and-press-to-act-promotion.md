# 0022 永続状態の整合・トランザクション化・押下時実行を coding / game-dev スキルへ昇格

## 背景・問題

2026-07-26〜27 の戦国風雲記の作業で、**同じ症状（右上「ターン終了」が効かない／「操作を完了できませんでした」）を3回、別々の原因で修正**した。同一テーマでの3連続の手戻りは、ルール化されていない一般則がある強いシグナルである。

- **1回目**（`01ad5e6`）: 画面固定ボタンを「押下位置を覚えて離した位置で判定」する実装にしていたため、高DPI・全画面・タッチ対応ブラウザで pointer release が Canvas 外扱いになるとボタンが無反応のまま失われていた。
- **2回目**（PR #288 / `eb1eeb1`）: 前日追加した大名（木曽家）の居城となる洲が province 未定義のまま参照だけ残り、ターン処理で例外。**該当データ1件を足す対症療法**で終えた。
- **3回目**（PR #289 / `b6fade5`）: 2回目の修正では足りず別大名・別武将で再発。真因は3つ重なっていた。
  1. `_endTurn` が「収入計上 → AI思考 → ターン確定」と state を直書きしながら進むため、途中で例外が出ると**収入だけ確定した半端な状態**が残る。ボタンを押すたび収入計上からやり直すので**金銭だけが積み上がっていた**。
  2. 例外源は DATA（洲・武将・大名）とセーブの不整合。DATA はリリースごとに増え城編集でも動くが、セーブは保存時点のスナップショットなので片側欠損が起きる。
  3. 削除した城を起動時のCSV取込が DATA にだけ復活させ、**取込が自ら不整合を作り出していた**。

さらに同日、戦闘画面の下部UI列が `y = H - 160` に高さ144pxのボタンを置いて余白16pxしか残らず、ブラウザ枠・セーフエリアで下辺が欠けていた（`2597b9b`）。

## 決定

再利用可能な一般則を、最も狭く効く2つのスキルへ差分追記で昇格した（既存ルールの変更・振る舞いの変更は行っていない）。

**`.claude/skills/coding/SKILL.md`**
1. 既存「デバッグ手順」へ3項追記 — ①`catch` のユーザー向けメッセージに例外の要旨を必ず含める ②**同じ症状を2回直したら1回目は対症療法だったと判断**し、欠損が生まれる経路を洗い出す ③「操作するたびに状態が悪化する」は非冪等な再試行のシグネチャで、原因箇所の特定よりトランザクション性を先に疑う。
2. 既存「外部データ取込のマッチング」へ1項追記 — 取込はユーザーが削除したエンティティを復活させてはならない（新規作成・既存更新の両経路でスキップ）。
3. 新セクション「**永続状態とマスタデータの整合**」— 読み込み時の正規化層1本化、マスタが変わりうる全入口での実行、後から増えた項目は"未登場"の既定値で補完、最下層アクセサの欠損耐性、"旧セーブ相当"を合成した検証（修正前コードで再現することの確認まで）。
4. 新セクション「**多段の状態更新はトランザクション化する**」— スナップショット→実行→失敗時ロールバック、確定済みの段を二重実行しない、理想は「計算→一括反映」でロールバックは既存構造を壊さないための現実解。
5. frontmatter の `description` に上記2テーマを追記（「旧セーブが壊れる」「再試行で状態が悪化する」で発火するように）。

**`.claude/skills/game-dev/SKILL.md`**（既存「固定Canvas UIのモバイル可読性対策」へ2項追記）
6. **画面固定ボタンは press（押下）で実行し release を待たない** — ヒット判定は `justPressed` で確定して即実行し、ドラッグ処理はボタンに当たらなかった場合のみ開始する。
7. **画面下端のUI列はセーフエリア分の余白を確保する** — `y = H - actionBottom - actionH` の形で算出（余白72px目安）。下端からの決め打ちを禁じる。

## 理由

- 3件の症状はすべて「Canvasゲーム＋永続セーブ」という本リポジトリの標準構成に固有かつ再現性が高い。sengoku.html 限定の事象ではなく、GameKit を土台にする今後のゲーム全てに効く。
- 昇格先を coding / game-dev に分けたのは「狭く効かせる」原則による。永続データの整合とトランザクション化は Canvas に限らないため coding、押下時実行と下端余白は固定Canvas UIの話なので game-dev の既存セクション（[[0019-fixed-canvas-mobile-ui-promotion]] で新設）へ寄せた。
- 「削除済みエンティティを取込が復活させない」は [[0014-import-matching-and-grid-verification-promotion]] で作った既存セクションの自然な延長のため、新設せず追記で強化した。
- 「同じ症状を2回直したら対症療法」は、`/self-improve` が最優先の昇格候補とする「再発・反復」の判定を**開発中にその場で使える形**にしたもの。振り返りを待たずに構造的原因へ向かわせる効果を狙っている。

## 影響・トレードオフ

- coding スキルが4セクション→6セクションに増える。肥大化の懸念はあるが、いずれも実際のバグ3件で実証済みの内容であり、抽象的な一般論は入れていない。
- 正規化層とロールバックはどちらも実行時コストを伴う（`structuredClone` 等）。ターン制のような低頻度の境界でのみ使う前提で書いており、毎フレームの処理へ適用する指示にはしていない。
- 昇格したのは「実装要件」であって機械検査ではない。永続データとマスタの整合は静的解析で検出しにくく、harness-lint への追加は見送った（検証手段として「旧セーブ相当の合成テスト」をスキル側に明記することで代替）。

## 併せて実施: 週次 `/self-improve` Routine の記載を実態へ是正

[[0021-routine-schedule-single-source]] で「初回firing 2026-07-26 の結果で要確認」としていた件の答えが出た。**初回firing（07-26 21:10 JST）は成功扱いで終了したが、`claude/self-improve` ブランチ・PR・Daily のいずれも残っていない**。この日は 17:23 JST まで作業コミットがあったため、prompt 手順2が働けば遡及Dailyは生成されていたはずである。

当初は「prompt が固定ブランチを指示する一方、ハーネスがセッションへ `claude/recursive-self-improvement-<乱数>` を割り当てるため指定が通らない」ことが原因だと考えた。しかし **`/agent-evolve` の Routine は固定ブランチ `claude/agent-evolve` で正常に動作し PR #272 を維持している**ため、固定ブランチ方式そのものが壊れているわけではない。**原因は未特定**であり、確実な事実は「初回firingが痕跡ゼロで終わった」ことと「本セッションを含め、ハーネスが作業ブランチを指定してくる場合がある」ことの2点にとどまる。

深澤の承認（「表を実態へ合わせる」）を得て、以下を実施した。

1. **CLAUDE.md の Routine 表**の `/self-improve` 成果物欄を「ローリングPR `claude/self-improve`」から「PR（作業ブランチは下記※）」へ変更し、脚注で実態を明記 — ハーネスの指定があればそれに従い、無い場合のみ固定ブランチを使う。あわせて初回firingが痕跡ゼロだった事実と「次回以降は痕跡が残ったかを翌セッションで確認する」ことを注記した。
2. **Routine prompt を更新**（`trig_01DuSy2rzQfPUcizikGGYJJg`）— ①ハーネスの作業ブランチ指定があれば必ず従う／無ければ固定ブランチ、のどちらでも動く記述へ変更 ②**「昇格すべき学びが無く変更しない週でも、その旨をDailyへ1行記録してコミット・プッシュし、痕跡を残す。無言で終了しない」**という条項を追加した。原因が未特定である以上、次回も同じ結果になりうるため、**痕跡を残すこと自体を義務化して切り分け可能にする**のが狙い。
3. 残課題: 検査#11 は曜日・時刻しか照合せず、成果物欄・ブランチ名のドリフトは機械検査できない。またRoutineの実行結果そのものはCIから読めないため、次回firing（2026-08-02）の痕跡を翌セッションで人手確認する必要がある。
