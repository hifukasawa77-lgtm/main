# 0022 Routine実行痕跡マーカーの導入と、セーブ⇄マスタデータ差分の恒久ルール化

## 背景・問題

2026-07-26〜28 の3日分がVault未記録のまま溜まり、そこに2系統の問題が埋まっていた。

1. **同一症状の4連続手戻り**: 戦国風雲記の「ターン終了ボタン」不具合を1日に4回修正した（`eb1eeb1`/`6c46cdc`/`01ad5e6`/`b6fade5`、PR #288・#289）。1回目は欠けていたデータを足す対症修正で、同種の欠損が今後も入る構造には触れていなかったため再発した。根治は「セーブとマスタDATAの差分を読み込み時に吸収する正規化層」＋「ターン処理のトランザクション化」。加えて汎用エラー文言（「操作を完了できませんでした」）が4回の手戻りの間ずっと原因追跡を妨げていた。
2. **週次Routineの無言の故障**: `/self-improve`（07-26 発火）と `/site-proposal`（07-19・07-26 発火）が、ブランチ・PR・Issue・Vault写し・Dailyのいずれも残さずに終了していた。実行実態はCCRのAPI側にありリポジトリから読めないため、「起動しなかった」のか「起動して何も出さずに終わった」のかを誰も判別できず、`/site-proposal` は2週間気づかれなかった。

## 決定

**A. コード実装の一般則を最も狭く効く場所へ昇格**

| 学び | 還元先 |
|---|---|
| 永続セーブとマスタデータの差分吸収（正規化層を1箇所／参照解決の最下層を欠損耐性に／参照IDと定義側の機械照合／削除のtombstone／旧セーブ合成での検証） | `.claude/skills/game-dev/SKILL.md` 新セクション |
| 多段state更新のトランザクション化（スナップショット→実行→失敗時ロールバック／再入時の二重適用防止／「押すたびに一部の数値だけ増える」は途中失敗のシグネチャ） | `.claude/skills/coding/SKILL.md` 新セクション |
| 捕捉した例外の要旨をユーザー可視フィードバックへ載せる（汎用文言だけは握りつぶしと同罪） | `.claude/skills/coding/SKILL.md` デバッグ節の強化 |
| 同一症状の修正が2度目なら対症でなく発生機構を直す／報告された症状の付随情報を捨てない | `.claude/agents/code-generator.md` 実装品質の基準 |

**B. Routineの無痕跡終了を禁止し、機械検査を置く**

- `/self-improve`・`/site-proposal`・`/agent-evolve` の各SKILL.mdに、**当日のDailyへ実行痕跡マーカー `<!-- routine:<skill> -->` を1行必ず書く**義務を追加した。成果ゼロ（昇格なし・提案なし・改善ネタなし）でも、その旨1行＋マーカーを書いてコミット・プッシュしてから終わる。
- harness-lint に**検査#13**（週次Routineの実行痕跡マーカーの鮮度／閾値10日＝週次7日＋猶予3日／警告△のみ・exit codeに影響しない）を追加した。

## 理由

- **痕跡の判定基準を専用マーカーに限定した理由**: 初期案の「Dailyがスキル名に言及していれば痕跡あり」では、**検査結果を報告するDaily自身が痕跡を偽造**して永久に✓になる（自己充足）。他セッションの言及と混ざらない専用マーカー行だけを判定基準にすることで、検査対象と検査結果の記録を分離した。
- **実態が読めない領域では代理指標を選ぶ**: Routineの実行実態はAPI側にあり、CIからは検査できない（[[0021-routine-schedule-single-source]] の「実態がAPI側にある設定は機械検証できない」の続き）。検査可能なのはリポジトリに残った痕跡だけなので、**スキル側に痕跡を残す義務を課してから**鮮度を見張る、という順序で設計した。
- **非ブロッキング（△）にした理由**: 痕跡が無い理由（未起動／無痕跡終了／その週は正当に何もしなかった）の切り分けはLLM作業であり、CIを赤にする性質のものではない。検査#8/#9 と同じ扱いに揃えた。

## 影響・トレードオフ

- 検出できるのは「痕跡が残っていない」ことだけで、**未起動と無痕跡終了は依然として区別できない**。ただしどちらも要調査である点は変わらないため、実用上の損失は小さい。
- マーカーを書く義務がスキル側にあるため、**スキルを経由しない手動実行では痕跡が残らず偽陽性の△が出る**。手動実行時もマーカーを書けば解消する。
- 導入直後は3件すべて△（マーカー未導入のため）。`/self-improve` は本日分で✓になり、残り2件は次回の各Routine発火で解消するはず。**08-03 の発火後も△が残るなら、Routine側の設定（環境・MCP権限）の問題**として切り分ける。
- 検査#13は `obsidian-vault/` を読むが、`.github/workflows/harness-lint.yml` の監視パスには**意図的に追加しない**（警告のみでexit codeに影響せず、Daily追記のたびにCIが回るだけになるため。検査#8/#9と同じ判断）。
