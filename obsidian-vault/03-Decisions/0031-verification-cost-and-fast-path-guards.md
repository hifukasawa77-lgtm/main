# 検査の反復コストを測って分ける（速い経路＋抜け道が広がらない検査）

## 背景・問題
深澤から「こちらの会話に対しての応答速度を上げて下さい」との指摘。
zero-1-local-ai の作業で「直す→確かめる」を何十回も回しており、1回あたりの確認時間が
そのまま体感速度になっていた。

推測せず実測したところ、各段の所要は **ビルド40秒 / テスト本体4秒 / 型検査6秒 / lint 12秒**。
`npm test` は `npm run build && node --test` の形で、**毎回40秒のビルドを踏んでいた**。
さらに調べると、ビルド成果物（`dist/server/index.js`）を読む検査は **241件中1件だけ**だった。
つまり待ち時間の9割が、その1件を走らせるためだけに払われていた。

## 決定
1. zero-1-local-ai に反復用の `npm run test:fast`（ビルド無し）を追加する。**44秒 → 1秒**。
   コミット前のゲート `npm run check` は従来どおりフル実行のまま。
2. 「速い経路」が骨抜きにならないよう、次の4点を検査で機械的に固定する:
   - `npm run check` が `test:fast` を使っていたら落とす
   - 飛ばす検査が1件を超えたら落とす（ビルド成果物を読む検査が増えたときも落とす）
   - **フル実行なのに1件でも飛んでいたら落とす**
   - 飛ばす際は理由付きで SKIP 表示する（`--test-skip-pattern` は使わない）
3. 一般則を `workflow` スキルへ「Skill: 検査の反復コスト」として昇格する。

## 理由
- **推測で速くしない**。「ビルドが重いのだろう」と思っても、実測しないと *何件のために* 重いのかが
  分からない。40秒 : 1件という比が分かって初めて「分ける」判断ができた。
- **速い経路は必ず抜け道になる**。速い方に慣れて重い検査が一度も走らなくなる、が典型的な失敗。
  ゲート側をフル実行に固定し、抜け道の広がりを検査で止める。
- **飛ばし方に落とし穴がある**。`--test-skip-pattern` は検査を一覧から消すので `# skipped 0` と
  表示され、外した事実が画面に残らない。npm が渡す `npm_lifecycle_event` で分岐し、
  理由付きで SKIP させる形にした。
- **成果物の有無での自動判定は偽の合格を生む**。前回のビルドが残っている環境では、
  古い `dist/` に対して緑になる。「古い成果物で緑」より「飛ばして明示」の方が安全。

## 影響・トレードオフ
- 反復中は1件（サーバ描画の検査）が走らない。コミット前の `npm run check` で必ず走るので、
  取りこぼしはゲートで止まる。
- 検査が4件増えた（241件）。うち「フル実行で1件も飛んでいないこと」の検査は、
  **後から足した**もの。最初の3件だけでは SKIP 条件を常時ONに壊す改変がすり抜けた
  （故障注入で発覚）。抜け道を作るときは「抜け道が閉じていること」自体の検査が要る。
